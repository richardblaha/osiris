# CLAUDE.md — digital twin

Details of `server/digital-twin` (API) and `server/digital-twin/web` (PWA); the repo-wide picture is in the root CLAUDE.md.

```bash
pnpm --filter @osiris/digital-twin dev   # API :3004, PWA :5175; needs a Kubernetes API (KUBE_*) and ClickHouse (CLICKHOUSE_*)
```

**Overview** (`server/digital-twin` + `server/digital-twin/web`, namespace `osiris`, https://twin.k6labs.cz): a general digital twin system as a 3D WebGL PWA (React Three Fiber over three.js, the OSIRIS theme: osiris-theme's tokens, generated into `web/src/theme.css`) — nested translucent shells of what each twin contains, gaps between siblings — monochrome: every solid, line and label is the accent's cyan at some transparency (dark scheme: #00f2fe), no grey or black; only what has a problem (a warning or an error) is magenta (the theme's secondary accent), and the selection glows the stronger accent. **Models are DTDL v3** (`@osiris/shared/dtdl.ts`: types, `interfaceErrors`, `resolveContents` with `extends`, `twinErrors`/`relationshipErrors`, localized `displayName`s, and the `dtmi:osiris:presentation;1` context's `presentation` section that says how the views draw a model's twins) and **instances follow the Azure Digital Twins API**.

**Where the data lives.** SQLite (`DATA_DIR/twin.db`, schema 3) keeps only the **definitions**: the DTDL models (the source's, marked `origin = 'source'`, plus the admins' own edits, which the sync never overwrites; a deleted source model stays as a decommissioned tombstone), the instances with settings and sealed secrets, dashboards, saved filters and each user's preferences. The twins' **current state** (twins, relationships, the view's telemetry aggregates) is written by each sync into **Redis** (`src/state.ts` `TwinStateStore`; keys `<REDIS_KEY_PREFIX>:twin:<instance>:…`, the telemetry expiring), the answers' cache is Redis too (`src/cache.ts` `redisCache`), and the collector's `twin_events` processor appends every warn/error log record to the `<prefix>:otel:events` stream (`GET /api/instances/:instance/events`, `GET /ops/events` for the agents). The history still goes out as OpenTelemetry events and is read back from ClickHouse; the telemetry pages (logs, metrics, traces) still query ClickHouse, with `?at=` for the past.

**Twins (instances).** It holds any number of twins (table `instances`, `src/instances.ts` `Instances` runs each one's source, sync, history and telemetry and restarts it when changed): each is a kind of source from the **registry** (`src/sources/registry.ts` `SOURCE_TYPES`: fields of its settings form, secret fields write-only and sealed with `TWIN_SECRETS_KEY` (`SecretBox`), a zod schema, `create` → adapter + `Telemetry`; today `kubernetes`: the cluster the service runs in or a pasted kubeconfig (`parseKubeconfig`: token only, inline only, no files), Ceph managers, its telemetry's ClickHouse (empty: the service's own) and cluster name), managed by admins (`/api/source-types`, `/api/admin/instances[/:id]`, the PWA's `Instances.tsx` behind the twin menu in the bar, `InstanceMenu.tsx`: each twin's Settings and Models tabs — picking a twin there shows it, so its DTDL models are the ones `Models.tsx` edits); `/api/instances` lists the twins the user may see, and every twin route below lives under `/api/instances/:instance` (the PWA's `api.ts` prefixes them with the chosen twin, kept in the URL as `twin=` and in `localStorage`). The first start with none makes one from the old one-twin settings (`src/bootstrap.ts`: `CLUSTER_NAME` as its id, so its history goes on; it takes the one twin's dashboards and filters, `claimLegacy`, and the Osiris dashboard; once — deleted, it stays deleted).

**API** in the shape of Azure Digital Twins (`$dtId`, `$etag`, `$metadata.$model`; relationships `$relationshipId`/`$sourceId`/`$relationshipName`/`$targetId`): `/api/models[/:id]` (admins may also `PUT /models/:id`, `POST /models`, `DELETE /models/:id` — validated with `interfaceErrors`/`presentationErrors`, a delete refused with 409 while a twin instantiates the model), `/api/digitaltwins/:id` with `/relationships` and `/incomingrelationships`, plus the lists `/api/digitaltwins` and `/api/relationships` (live from Redis; `?at=` a past time from the history), `/api/digitaltwins/:id/history`, `/api/history/range`, `/api/events` (the collector's warn/error stream) and the models' telemetry `/api/telemetry/errorLogs`, `/api/telemetry/storage` (each volume claim's filesystem: `used`, `fsCapacity` from kubeletstats' `k8s.volume.capacity`/`available`, named by the claim only with the agent's `extra_metadata_labels: [k8s.volume.type]`, the adapter's `storageMetrics`, `Telemetry.latest`), `/api/telemetry/resources` (the hardware's and the workloads' readings, `ResourceReading` in `src/state.ts`: a core's, CPU's, memory's and disk's `load` 0–1, `used`/`size`, a disk's `io` B/s, a CPU's, memory's or NVMe disk's `temperature` in °C, a container's and pod's `cpu` cores and `memory` bytes, `estimated` for a core shown at its CPU's average; the source maps its own metrics, `TwinSource.resources`, the Kubernetes one `kubernetesResources`: kubeletstats `k8s.node.cpu.usage`/`memory.working_set`/`filesystem.*`, `container.*`/`k8s.pod.*` cpu and memory, the agents' hostmetrics `system.cpu.utilization` by `cpu` where `state` is idle and `system.disk.io` by `device`, node-exporter's `node_hwmon_temp_celsius` by `chip`/`sensor` (the CPU's chip, the memory's, an NVMe's — each part takes its hottest) — `Telemetry.latest`/`rates` take point attributes, `KeyedBy`) and `/api/telemetry/network` (bytes/s of nodes and pods, the adapter's `networkMetrics`: kubeletstats' `k8s.node.network.io`/`k8s.pod.network.io`, rated over 5 minutes; `Telemetry.rates`; a twin without its own counter, like a microk8s node, carries its children's in the view). Live telemetry answers come from Redis (the sync writes them); `?at=` from ClickHouse.

**Models and sync.** Every model extends `dtmi:osiris:twin:Entity;1` (`name`, `status`, `otelResource` = the OpenTelemetry resource attributes of its telemetry, Telemetry `errorLogs`), and may carry a **`presentation`** section (`dtmi:osiris:presentation;1`: `look` — one of `LOOKS`, else the built-in of its DTMI, else a box; `color`, `icon`, `label` — a property name, `layer` — base/hardware/network/services/storage/namespaces/workloads (a workload's then by its kind; the older `logical` reads as namespaces), else the built-in of its DTMI (`BUILTIN_LAYERS`; a LoadBalancer or public interface is the services', a node's card — its LAN port — the hardware's), `visible`, and `visual` — the model's own drawing, see Rendering): the 3D view draws each twin as its model's presentation says (`buildScene` in `web/src/scene.ts`), so an admin changes the rendering by editing the model (the Models tab of a twin in the twins' administration, `Models.tsx`: a visual form and the DTDL in Monaco (`CodeEditor.tsx`, loaded on demand from the app's own build with the JSON worker, a theme made from the page's OSIRIS variables, a JSON schema of the supported DTDL and presentation while typing)). A **source adapter** (`TwinSource` in `src/twin.ts`: `models()`, `snapshot()`, `errorAttributes`, `networkMetrics`, `storageMetrics`) reads a system; `src/sync.ts` validates its models into SQLite (admin-edited ones are left alone) and every `SYNC_INTERVAL_SECONDS` diffs the snapshot against the last one in memory (`diffSnapshots` in `src/state.ts`), writes the after state and the view's telemetry into **Redis** (atomically, telemetry with a TTL) and sends what changed as **OpenTelemetry events** (`src/history.ts` `HistoryLog`, `eventEmitter` of `@osiris/platform/telemetry.ts`: `twin.entity`/`twin.relationship` log records with `twin.id` = the instance, `dt.*`/`rel.*` attributes and `dt.ancestors`, a checkpoint of everything once a day) into ClickHouse's `otel_logs`; `HistoryReader` rebuilds any time from the newest checkpoint plus the changes (30 days, the logs' TTL).

**The collector's events.** `deploy/observability/twin-events` is a Go processor (`twin_events`) built into the cluster's collector image (`cmd/otelcol/main.go` lists the components, built by that folder's `Dockerfile`, no ocb; `deploy/observability/collector.yaml` runs it in the `logs` and `logs/agents` pipelines): every log record at least `min_severity` (warn by default; the severity is inferred from the body like `SEVERITY_EXPR` when the record carries none) is appended to the Redis stream (XADD, MAXLEN-capped, best effort — ClickHouse never waits on it). The API serves it at `/events`, the agents at `/ops/events` (the `twin_events` tool in `packages/tools/digital-twin`), and the alerting service turns them into alerts (below).

**Rendering** (`web/src/Twin3D.tsx`, `web/src/three/`): a React Three Fiber `<Canvas>` (`flat`: no tone mapping, so the theme's colours stay as they are) over the layout of `TwinLayout.ts`. Each solid is a `Solid` drawn by its **look**, a React component of the registry `LOOK_COMPONENTS` in `three/looks.tsx` (by the box's shape, else the twin's `presentation.look`: box, node, cluster, drive, switch, router, firewall, ap, cylinder, drum, hex, gate, port), in its own frame centered on its box, its body registered for picking (`Body`); a new look is a component there and an entry in the registry. How each solid looks now (shown, faded outside the selection, standing out, colours, fill, activity) is one `Appearance` (`three/paint.ts`, `appearanceOf`) worked out from the view's state (`ViewState`: selection, hovered twin, traffic path, layers, theme colours), and a solid is drawn again only when its appearance changes (`sameAppearance`); animations (lights blinking with traffic, rotors, sweeps, pulsing cables) run in `useFrame` on refs, never through React state. The links (lines, interface dots, packets, cables as tubes, the internet's globes) are `three/Links.tsx` (`linkPaintOf` colours them), the labels' level of detail and the interfaces' addresses `three/Labels.tsx` (three.js CSS2D, rendered after the scene by `Render`), the camera (orbit, fit, flights, keyboard and agent steering, the callout anchor) `three/Camera.tsx`, the pointer's picking and tip `Picker`. Geometry helpers are `three/geometry.ts`, the labels' and tip's texts `three/info.ts`.

**Where the values come from.** Every value a model's twins get is told in the model's `dataProfiles`: a connection's (the data hub's, `live`, a simulation, a replay) or the source's own, in the profile `source` (`sourceProfile` in `sources/kubernetes/readings.ts`) whose bindings name the reserved connection `source` (`SOURCE_CONNECTION`; no instance's connection may take that id, the hub never runs it, the active-profile list leaves such a profile out, model validation doesn't look for its connector): `reads` `clickhouse` (the reading of `READINGS` — the one list the adapter reads from too — its `metric`, `by` attributes, a `formula` and the `query` exactly as `readingQuery` in `telemetry.ts` builds what `Telemetry.rates`/`latest`/`errorCounts` run), `kubernetes` (the API object and field, `path`) or `ceph` (the manager's metrics). The twin's detail shows them under "Where the data comes from" (`DataOrigins.tsx`, the query expandable).

**A model's own drawing** (`presentation.visual`, `@osiris/shared/visual.ts`, validated by `visualErrors` within `interfaceErrors`, a JSON schema in `CodeEditor.tsx`): data, never code, so an edited model can't run anything in a viewer's browser — up to 64 parts, each a primitive (`box`, `cylinder`, `sphere`, `plane`) in the solid's own frame, positions and sizes as fractions of the solid's size (so it fits whatever size the layout gives), with a colour (`#rrggbb` or the theme's `status`, `accent`, `active`, `neutral`, `warn`, `error`, `level` = its value's band), opacity, outline, and what it follows by a value's name (`visualValue` in `scene.ts`: the view's readings `fill`, `network`, `status`, `errors`, `load`, `io`, `cpu`, `memory`, `used`, `size`, else a property; `a/b` a ratio): `fill` (grows along an axis), `blink` (bytes/s), `spin`, `repeat` (copies, a count or a value) and `when` (`name` or `name=value`). A `gltf` part places one of the instance's **3D assets** by name (`asset`), fitted into its size keeping its proportions, in its own (lit) materials, tinted by `color` when given: assets are binary glTF (GLB) that hold everything themselves — `glbProblems` in `src/assets/glb.ts` refuses a buffer or image outside the file and any extension needing a decoder (Draco, meshopt), at most 8 MB — in SQLite's `assets` (base64), put and deleted by admins (`PUT|DELETE /api/instances/:id/assets/:name`, the administration's "3D models" tab, `Assets.tsx`), read by the twin's viewers (`GET …/assets[/:name]`, an ETag of its SHA-256, a sandbox CSP), loaded once per name in the view (`loadAsset`, `GLTFLoader.parseAsync` of the bytes fetched with the user's token). The Models tab edits a drawing in a form (`VisualEditor.tsx`: the preset, over or instead of the look, each part's fields, the server's errors as it would answer them) beside a live preview of one solid of the model on flat, cubic or upright proportions, drawn by the 3D view's own `Solid` (`VisualPreview.tsx`, loaded on demand). **Built-in assets** (`assets/*.glb`, made by `web/scripts/assets.mjs` from three.js primitives at real size in millimetres, no badge or brand: a mini PC, a home router with four antennas, a desktop switch, a 2.5" USB disk) are every twin's (`builtinAssets` in `src/assets/builtin.ts`, checked like an upload, listed with `builtIn`, never deleted; an instance's own of the same name wins). **Presets** (`VISUAL_PRESETS`: `mini-pc` (the asset stretched to the machine's solid, see-through), `mini-pc-shapes`, `router`, `switch`, `usb-disk` (their assets, `fit`), `drive`, `level-x`, `level-y`; a `gltf` part's `fit` is `contain` or `stretch`) are drawings too, and the built-in looks of a machine, a router, a switch, a disk and a core or memory are drawn from them over a plain box (`PRESET_LOOKS` in `three/looks.tsx`), the router, switch and USB disk presets draw the device whole (`WHOLE`: the plain box gives way to the outline and the picking body); a model takes one with `preset` (its parts first, then the model's own) or copies its parts to change them; the looks whose drawing the schema can't say (a port's socket, Ceph's gauge, a Service's sweep, an Ingress, storage cylinders) stay components. A colour `body` is the solid's body as the view paints it; `when` takes `!` to turn round. `mode: "add"` (default) draws the parts over the model's look, `"replace"` instead of it (`OutlineLook`: the outline and an invisible picking body stay). `three/visual.tsx` draws them (`VisualParts`, one shared unit geometry per shape, blinks and spins in `useFrame`).

**The 3D view.** The PWA (`web/src/scene.ts`) builds the view only from DTDL: `contains` nests twins, statuses and `errorLogs` roll up, labels and property formatting come from the models; children sit in a cube-like 3D grid (`arrange`/`cubeGrid` in `TwinLayout.ts`: columns, rows and layers from the floor up, groups by model lined up along the axis that keeps the whole nearest a cube; leaves are cubes), so the twin is a block rather than a plate; boxes have slightly rounded edges and storage (a model with Telemetry `used`) is a cylinder filled as far as it is full; twins whose model declares Telemetry `network` get a line from a hub (the bridge, else the router) on their container's back wall to their port or back wall with packets moving by their load, a pod's containers a line to its eth0 (`lan`), related siblings (a container `mounts` a claim) a line over their tops, and only the router's WAN port reaches the internet, a globe behind it, over an Ethernet cable (LoadBalancers are never wired to the internet directly) — every line is orthogonal (`orthogonal` in `TwinLayout.ts`: segments along one axis, right-angle turns, never straight across; network links run in a tray under the children's floor, wires and tunnels in lanes behind the back walls, routing and storage relations over the tops), ends on a wall, mantle, port or the globe, marked as an interface, and carries its layer (`Link.layer`) (`TwinLayout.ts`, `Twin3D.tsx`); a twin outside the containment tree that relates to one inside it groups it (`project` in `scene.ts`): the outermost group, a namespace, is a band — one dashed solid across the cluster around all of it, in every node and outside them (`measureBanded` in `TwinLayout.ts`: the nodes are columns, each band a row across them, what no node holds a wall-less column, what no band (disks, Ceph) the last row; the band rows go one behind another in levels stacked as high as keeps the cluster nearest a cube) — and the inner groups, workloads, are projections in each node (their telemetry is their group's on the node); each kind of twin has its own look (its model's `presentation.look`, else the built-in of its DTMI, `BUILTIN_LOOKS` in `@osiris/shared/dtdl.ts`: the cluster on a floor grid, a node with a status light, a namespace dashed and tinted, a workload dotted, a container solid, storage a filled cylinder, a disk with platters, Ceph (`ceph`) a disk array of two columns — the physical disks lying flat and stacked on one another in the left column (USB-disk look with the connector at the back, each showing its fill), the pools as flat round discs stacked in the right column (the distinction, no connector), a gauge on its lid as far round as it is full and a halo that pulses while unhealthy, the firewall (`firewall`) a plain box as big as a machine, on top of the stack, holding the whole virtual network (the one ingress controller twin with all routes, the Services, the LoadBalancer addresses, and the network components — calico, metallb), an access point (`ap`) a flat box with Wi-Fi waves, an interface a port on its container's wall by its kind (a router a disc, a tunnel a hexagonal disc, a bridge a bar, a Wi-Fi network waves, the rest plates), a Service a hexagonal outline, an Ingress a portal — two posts and a beam with a breathing membrane, a lock on the beam with TLS, its hosts in its label), interfaces are wired (`wire`, `overlay` dashed for VXLAN), routing (Service → pods' eth0 — ending on the inner side of the eth connector, Ingress → Service, LoadBalancer → Service) is drawn faint with the services layer and lit on the selection's traffic path (`pathOf`: public address → LoadBalancer → controller pods, Ingress → Service → pods → eth0 → router, lit with packets), storage relations (`hasOsd`, `holds`) dashed with the storage layer, lit when one end is selected; a twin, its lines and its address labels show only while its layer does (`hidden` in `Twin3D.tsx`); the only labels are text drawn on the solids' own faces as canvas textures (`TextPlate` in `three/looks.tsx`, `plateLines` in `info.ts`): a machine's name, and its parts' names with their readings — a core `cpu #1` with its load big and its CPU's temperature small with a thermometer pictogram, the CPU chip likewise, RAM and a disk (NVMe, USB HDD) with their name and their fill share big; nothing else is labelled (no floating labels or port addresses anymore); the 3D view is built once and repaints on refresh. Selected and hovered things glow stronger than the accent (`--accent-active`); interfaces with an address (pods, nodes, disks) show it beside their dot by level of detail.

**Hardware in the view.** The machines lie flat like mini PCs on a shelf, stacked one on another (`measureBanded` in `TwinLayout.ts`): the control planes on top, then the workers by name (`stackOrder`, the node's `role`), every machine the same size and its floor at least 2.6 times as wide and deep as it is high, the namespaces' bands in the same place on each (a floor plan kept near a square), so one dashed solid around a band takes in all of it through the machines' floors; what belongs to no machine (unscheduled pods) floats above the stack on the same plan; the firewall is a column of the stack itself — a box as big as a machine on its top, holding the whole virtual network of the cluster (the Ingresses, Services with their endpoints and the LoadBalancer addresses on its back wall), brick-walled between the internet and the machines. The cluster's own solid holds only that: Ceph (a storage cluster of its own, drawn as a disk array) and the LAN's devices (the switch, the router, any further one) stand outside it, Ceph beside it, the LAN's devices behind it. Each machine's hardware (`hardware` layer, looks `cpu`, `core`, `memory`, `drive`, `HARDWARE_LOOKS` in `scene.ts`) covers its whole floor on a board (`layoutDeck`, `measurePart`, `Scene.boards`): the CPU, memory and internal disks side by side, each a share of the width and the full depth; the CPU's cores as tiles covering it, each core, the memory and a disk filled as far as its `load` (cyan, warning from 80 %, error from 95 %; an estimated core paler; memory and disks along their length), its temperature coloured by its own band (warning from 80 °C, error from 90 °C) and shown in its label, a disk's activity light blinking with its I/O. Its USB disks lie flat, stacked in the storage cluster's array (`measureArray`: the left column of physical disks, each with the USB connector at its back where its cable plugs in from outside the disk, the right column of pool discs) when there is one, else on a shelf beside the machine and the cluster, each cabled straight from a USB-A port on the machine's right wall (`cable`); its network card is an RJ45 port on its back wall, cabled (`ethernet`) to the LAN's switch behind the stack, the switch's uplink to the router beside it, whose WAN port reaches the internet over an Ethernet cable — a solid tube to the globe (`DEVICE_LOOKS`, `rules.device`; without a switch the cluster's hub reaches each machine as before). Everything plugged in is drawn at the machines' real scale (`MM` in `TwinLayout.ts`: a machine 175 mm deep, an RJ45 16 mm, a USB-A 12 mm, a 2.5" disk, a 20 mm port pitch on the switch, a 230 mm router with 150 mm antennas, the cables' radius `Link.radius`). `Twin3D.tsx` draws the cables as solid tubes with plugs (`cableGeometry`) that pulse with their traffic (a disk's I/O, a machine's network), the ports as real sockets facing out of their wall (`Box.normal`: an RJ45's opening with its clip notch, contacts and link/activity lights, a USB-A's opening with its tongue), a machine's front as a mini PC's with a vent grille and a power button and light, the switch and the router as cyan see-through shells with their lights (the router's four antennas), never a badge or a brand. The OSD's DB on the NVMe is a storage line (`dbOn`); a selected container (or pod) lights its lines down to its node's CPU and memory (`resource`, `runsOn`), a selected CPU or memory every container on it. `layoutRules(scene)` in `scene.ts` is what the 3D view and the tests lay out with.

**Network services in the view.** A LoadBalancer (MetalLB) is a disc on the cluster's back wall with a rotor of spokes, one per node it hands traffic to, turning (faster on the selection's path); a Service's lid fans out a spoke per ready endpoint (up to 12) and a sweep hands requests to them in turn — kube-proxy's balancing — quicker while it is on the selected path; an Ingress the portal as before.

**The bottom bar.** Under the 3D view one bar (`web/src/BottomBar.tsx`) holds everything: the time axis (`Timeline.tsx`), the view's settings (`DisplayMenu.tsx`, the "tune" icon, a dialog over the whole window in four columns, closed by Escape, a click beside it or its button: the layer switches — hardware (the machines' CPU, cores, memory and disks, their ports and cables, the switch and the router), network (interfaces, bridges, routers, tunnels), network services (Services, Ingresses, LoadBalancer and public addresses), storage, namespaces, then one layer per kind of workload — Deployments, StatefulSets, DaemonSets, Jobs (CronJobs' too), bare ReplicaSets, standalone pods, other owners (`WORKLOAD_LAYERS`/`workloadLayer` in `scene.ts`, by the workload's `ownerKind`; a hidden kind hides its pods and their containers too, `hidden` in `Twin3D.tsx`), with each kind's Kubernetes icon and count (`LAYER_KEYS` in `Twin3D.tsx`; a stored `logical: false` or `workloads: false` switches the older groupings' layers off); the base always shows —, the drawing options (`DisplayOptions`: labels by size, all or none, the addresses, moving traffic), and the filters — hidden models, a lowest status, a name search; all kept in this browser, the filters applied in the scene, `passes` in `scene.ts`), a button per panel (properties, logs, metrics, traces, chat; `togglePanel`) that shows or closes it, lit while it shows, dim without a selection, and the chat with Osiris (`OsirisChat.tsx`: the input in the bar — its left icon a menu of a new conversation and the earlier ones, newest first, from Osiris's `/threads` — the conversation a window, `chatPanel`). The keyboard moves inside the model (`Twin3D.tsx`): WASD/arrows pan, Q/E down/up, +/- zoom, Tab/Shift+Tab cycle the selection, H the whole twin, 1–5 one infrastructure layer alone, 6 the workloads alone, 0 all of them.

**Interaction.** Hover names a box; a click selects it and the camera flies to center it with room around it, with its panels (`detailPanels` in `FocusPanels.tsx`: properties, a log tail of the 10 newest that loads older ones as it scrolls up, CPU/memory/network sparklines, traces) in windows over the twin joined to the box by SVG lines redrawn every frame; the first Escape closes the panels (the camera stays), the next flies back to the whole twin. **The windows** (`Windows.tsx`, the layout as data in `windowLayout.ts`) hold the selection's panels and the conversation with Osiris: each window a group of panels as tabs at a rectangle in fractions of the area; it moves by its header and docks in one of the area's 9 parts (`GRID_AREAS`: columns and rows 20 %, 60 %, 20 %, `snapRect`) when dropped on that cell of the compass shown in the middle while dragging (`.wm-compass`), at an edge or in a corner (the top edge maximizes), or from its menu's grid drawn to scale; a part holds one window (`dock`), so docking into a held one joins it as tabs; moving or resizing lets the dock go; it joins another window as tabs when dropped on its header, lets a tab dragged out become a window of its own, resizes by its edges and corners, maximizes (button, double click) and has a menu doing the same without dragging; a closed panel stays hidden until the view's settings show it again (also "Default layout"). Below 720 px the windows are one, every panel a tab. The layout is the user's: `PUT /api/me/preferences/layout` (table `preferences`, owner and key, the same in every twin; `normalizeLayout` makes a stored one safe), cached in `localStorage`, saved 0.8 s after the last change. A time axis (`Timeline.tsx`) and each twin's Changes.

**Kubernetes adapter.** The one adapter is Kubernetes (`src/sources/kubernetes/`, models `;3`: namespaces, pods, nodes, replicasets → `contains` is physical: cluster → nodes (and unscheduled pods) → pods → containers and the PersistentVolumeClaims they mount (`PersistentVolumeClaim;1`, in the first pod by name, an unmounted one in the cluster; containers `mounts` it; the ClusterRole lists `persistentvolumeclaims`, without it the twin goes without them); the hardware (`hardwareIds` in `graph.ts`, models `dtmi:osiris:hw:Cpu;1`/`CpuCore;1`/`Memory;1`/`Disk;1`/`Port;1`): each node's CPU with a core per logical CPU of its capacity, its memory, its disks — from Ceph's `ceph_disk_occupation` (`devices`, `device_ids` = model and serial): each OSD's data disk (sdX: USB by the twin's setting `externalDisks`, else SATA) with a USB port `attaches` it, and the other devices it uses (its DB on the NVMe) as internal disks, the first one carrying the root filesystem's telemetry, a stand-in `system` disk without Ceph; a USB data disk carries only its OSD, so the two are one twin: the disk takes the OSD's id, state and bytes (`osdId`, `up`, `in`, `used`, `fill`), and Ceph's `hasOsd` points straight at it; an OSD on an internal disk or an unknown host stays its own `CephOsd` twin, contained by its disk (else the node, else Ceph); their `otelResource` is the node's attribute plus `hw.component` (and `cpu`, `device`, `hw.rootfs`), never the node's alone; containers `runsOn` their node's CPU and memory); the network (`network` in `graph.ts`, model `dtmi:osiris:net:Interface;1` with `kind` physical/router/bridge/tunnel/veth/loadbalancer/public/external/wifi): each node's card, router (Calico's routes, no bridge; with a bridge CNI — flannel's annotations — the host's, with the bridge `cni0` on the node's pod CIDR) and VXLAN tunnel (from the node's Calico or flannel annotations), each pod's `eth0` wired to its node's bridge, else its router (`connectedTo`), Services (`Service;1`, `routesTo` the pods of their EndpointSlices, a warning without ready ones) with their LoadBalancer addresses (MetalLB, `exposes`), all Ingresses and IngressRoutes aggregated into the one ingress-controller `Ingress;1` twin (every host and route on it; `routesTo` Services, `servedBy` the controller's LoadBalancer, an error for a missing Service — no object per ingress resource), Services and LoadBalancer addresses, plus the network components (`dtmi:osiris:net:Component;1`: calico wired to the nodes' routers and tunnels, metallb to the LoadBalancer addresses) — all contained in one firewall twin (`dtmi:osiris:net:Firewall;1`, a box as big as a machine on top of the stack), and the public addresses the Ingress hosts resolve to (`publicAddressesOf`; Cloudflare's addresses become one CDN interface in front of the cluster's own); with the twin's setting `lan` (`switch`, the default) the LAN too: a switch (`dtmi:osiris:net:Switch;1`) with a port per node's card (`connectedTo`) and an uplink to a router (`dtmi:osiris:net:Router;1`) with a LAN and a WAN port, their make and model from `switchModel`/`routerModel`, plus any further device of the LAN from `lanDevices` (`kind:name` or `kind:model:name`, e.g. an access point `dtmi:osiris:net:AccessPoint;1` with an uplink on a free switch port and a `wifi` port) — all cabled (`connectedTo`) to the switch (`lanIds`); and the external services of `externalServices` (URLs probed at every sync, `probeService`; Mistral's API for the agent is the default) as `external` interfaces on the globe, reached only through the router's WAN port; a node's `role` is `control-plane` by kubeadm's or microk8s's labels, else `worker`; namespaces and workloads relate by `hasNamespace`/`hasWorkload`/`hasPod`/`hasClaim`; with `CEPH_MANAGERS` (the managers' Prometheus pages, the active one answers; `sources/kubernetes/ceph.ts`) Ceph is a twin in the cluster with what watching it needs (health and the raised checks of `ceph_health_detail`, OSDs up/in, monitors in quorum, placement groups active+clean and degraded, client read/write bytes per second from the pools' counters between syncs) and its pools (`holds` the claims whose PV is an image in it), and its OSDs merged into their USB data disks (each filled by its own bytes, `ceph_osd_stat_bytes[_used]`, else by the cluster's average), its DB on the NVMe as `dbOn`; namespaces and workloads carry their worst pod's status; ids are escaped paths `k8s:<cluster>/namespace/<ns>/pod/<pod>`).

**Pages and telemetry.** Telemetry and history answers are cached in the process (`memoryCache`). The twin is the PWA's only view under a see-through bar (pages centered, the user an avatar with a menu); the telemetry pages (Logy, Metriky, Trasy — the same ClickHouse queries the dashboard reads with) lie half see-through over it, closed by their tab again or Escape, and open filtered by the selected twin's `otelResource` (logs, traces and series take `namespace`, `pod`, `node`, `container`, `claim`). The first tab, Overview, opens a dashboard (with several, a menu asks which): named, shared dashboards (`/api/dashboards`, table `dashboards`, `Dashboard.tsx`) of panels — log bar charts, log records, metrics, traces — each with its page's filter and a width of four columns, over one time range; the pages add their current view to one ("+ Overview"). Logs show a bar chart of records over time by severity (`/api/logs/histogram`; hover shows a bar's counts, a click picks its time and level, a drag a span) and the user's saved filters (`/api/me/filters`, table `saved_filters` in `twin.db`, each user's own); their filters (service, namespace, node, pod, container from `/api/facets`, level, text searched as it's typed) live in the URL. A record's severity is its own, else read from its text (klog's prefix, a `level` field, the level's word, a Warning event; `SEVERITY_EXPR` in `telemetry.ts`), else info: most pods' output carries none, and the twin's error counts use the same. Without a token the PWA goes straight to sign-in (once a minute at most, so a failed sign-in never loops). The twin seeds an "Osiris" dashboard once (`src/dashboards.ts`).

**Osiris chat.** Osiris's agent lives over the twin (`OsirisChat.tsx`): the input at the bottom in the middle, the conversation a window over the twin (the state in `useOsirisChat`, shared by the input and the window), any earlier conversation opened from the history menu, voice messages (transcribed by Osiris, Mistral), answers read aloud (Piper), approvals as forms, and `twin_view`'s steps run on the view (select, turn/tilt/zoom through Twin3D's `control`, open pages, history); it calls Osiris through the twin's `/osiris/api/*` proxy (`OSIRIS_URL`, project `OSIRIS_PROJECT`) with the user's token, which osiris-gateway must accept from the `digital-twin` client: osiris-auth adds the apps in `GATEWAY_ACCEPTS` (`digital-twin,osiris-twin-alerts` in `deploy/auth`) to the gateway's app at every start — without it the gateway answers "Invalid token".

**Sign-in and storage.** Sign-in is osiris-auth's: the PWA signs in as the public client `digital-twin` (PKCE), the API introspects as `osiris-digital-twin`: the group `admin` (`AUTH_ADMIN_GROUP`) sees and manages every twin, the group `twin:<id>` sees that twin (`maySee` in `auth.ts`; another twin answers 404), anyone else gets 403. `CLICKHOUSE_*` is the service's own ClickHouse (the history's, and a twin's telemetry when it names none); a twin's telemetry cluster name is the `k8s.cluster.name` its collector's resource/cluster processor stamps telemetry with. Controlling the twinned system (DTDL `Command`s, desired state, audit) would go to PostgreSQL.

**Alerting** (`src/alerts`, its own image `osiris-digital-twin-alerts` and Deployment `digital-twin-alerts`, `deploy/k8s/digital-twin-alerts.yaml`; plan and next steps in `PLAN.md`): reads the `otel:events` stream with its own consumer group (`twin-alerts`), groups events into alerts (`AlertEngine`, `engine.ts`: a fingerprint of cluster, namespace, workload from the pod's name, container and the message's shape; repeats within `ALERTS_REOPEN_MINUTES` join, `ALERTS_RESOLVE_MINUTES` without events resolves; Redis `<prefix>:alerts:*`, 30 days) and has Osiris's agent investigate each new one in a new conversation of project `twin` (`osiris.ts`: diagnose and propose, change nothing; at most `ALERTS_MAX_PER_HOUR`). It is Osiris's user only as a service account: osiris-auth's app `osiris-twin-alerts` acts as the user `twin-alerts` (client credentials, `ALERTS_CLIENT_SECRET`, fetched again after 2, 5 and 15 s while osiris-auth answers 5xx, and anew after a 401), and osiris-gateway's app accepts its tokens (osiris-auth's `GATEWAY_ACCEPTS`). Only the twin's API asks it (`/alerts`, `/alerts/:id`, `/alerts/:id/messages`), with its ServiceAccount's token projected for audience `osiris-twin-alerts` (TokenReview; NetworkPolicy), through `alerts-client.ts` (`ALERTS_URL`); the twin serves `/api/instances/:i/alerts` (its cluster's only) and `/alerts/:id/messages`, and the PWA's chat history lists them: an alert's conversation is read-only, a reply goes on in a new conversation of the user's own with the alert's findings as context.

**Data sources** (`src/datasources`, plan in `PLAN.md`): a model's `dataProfiles` (context `dtmi:osiris:data;1`, `dataProfileErrors`/`dataProfilesOf` in `@osiris/shared/dtdl.ts`) bind its Telemetry or Property contents, per profile (`live`, `simulation`, `replay`; a simulation's `simulator` names its tool's connection and scenario), to a twin's **connections** (table `connections`, settings plus sealed write-only secrets; admins at `/api/admin/instances/:id/connections[/:conn][/check]`, the PWA's Data sources tab, `DataSources.tsx`): `CONNECTOR_TYPES` in `connectors.ts` — clickhouse (one SELECT, the twin's values as typed `{name:Type}` parameters, `readonly=1`), prometheus (PromQL, label values quoted), mqtt, kafka, rabbitmq (streams; values only as whole topic levels or routing keys, an exclusive queue), generator (simulated values) and kubernetes-simulation (the simulation's cluster; configuration only so far). Placeholders `{id}`, `{name}`, `{twin.<prop>}`, `{otel.<attr>}` (`template.ts`, `fill` with a per-place escape); this host and link-local addresses are refused. Saving a model checks its bindings against the connections (`bindingErrors`); a connection a profile reads can't be deleted. Each instance runs a `DataHub` (`hub.ts`) for its active profile (table `data_profile`, `PUT /api/instances/:i/data/profile`, default `live`): it plans every twin's bindings (at most 1000, made again every minute or on a change), polls the due ones four at a time (`every`, default 30 s), keeps one subscription per streaming connection, and writes values to Redis (`redisDataValues`, `<prefix>:twin:<instance>:data`); `/api/instances/:i/data` lists the profiles and the hub's status (connection errors for admins only), `/data/values?twin=` the active profile's values, shown in the properties panel.

**The agent and the windows.** `twin_view`'s `window` steps (show, close, focus, maximize, restore, snap, merge, detach a panel: properties, logs, metrics, traces, chat) and `layout` reset run on the user's layout through `windowStep` (`windowLayout.ts`).
