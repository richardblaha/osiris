# CLAUDE.md — digital twin

Details of `server/digital-twin` (API) and `server/digital-twin/web` (PWA); the repo-wide picture is in the root CLAUDE.md.

```bash
pnpm --filter @osiris/digital-twin dev   # API :3004, PWA :5175; needs a Kubernetes API (KUBE_*) and ClickHouse (CLICKHOUSE_*)
```

**Overview** (`server/digital-twin` + `server/digital-twin/web`, namespace `osiris`, https://twin.k6labs.cz): a general digital twin system as a 3D WebGL PWA (three.js, the OSIRIS theme in cyan and magenta) — nested translucent shells of what each twin contains, gaps between siblings, edges coloured by status. **Models are DTDL v3** (`@osiris/shared/dtdl.ts`: types, `interfaceErrors`, `resolveContents` with `extends`, `twinErrors`/`relationshipErrors`, localized `displayName`s, and the `dtmi:osiris:presentation;1` context's `presentation` section that says how the views draw a model's twins) and **instances follow the Azure Digital Twins API**.

**Where the data lives.** SQLite (`DATA_DIR/twin.db`, schema 3) keeps only the **definitions**: the DTDL models (the source's, marked `origin = 'source'`, plus the admins' own edits, which the sync never overwrites; a deleted source model stays as a decommissioned tombstone), the instances with settings and sealed secrets, dashboards, saved filters and each user's preferences. The twins' **current state** (twins, relationships, the view's telemetry aggregates) is written by each sync into **Redis** (`src/state.ts` `TwinStateStore`; keys `<REDIS_KEY_PREFIX>:twin:<instance>:…`, the telemetry expiring), the answers' cache is Redis too (`src/cache.ts` `redisCache`), and the collector's `twin_events` processor appends every warn/error log record to the `<prefix>:otel:events` stream (`GET /api/instances/:instance/events`, `GET /ops/events` for the agents). The history still goes out as OpenTelemetry events and is read back from ClickHouse; the telemetry pages (logs, metrics, traces) still query ClickHouse, with `?at=` for the past.

**Twins (instances).** It holds any number of twins (table `instances`, `src/instances.ts` `Instances` runs each one's source, sync, history and telemetry and restarts it when changed): each is a kind of source from the **registry** (`src/sources/registry.ts` `SOURCE_TYPES`: fields of its settings form, secret fields write-only and sealed with `TWIN_SECRETS_KEY` (`SecretBox`), a zod schema, `create` → adapter + `Telemetry`; today `kubernetes`: the cluster the service runs in or a pasted kubeconfig (`parseKubeconfig`: token only, inline only, no files), Ceph managers, its telemetry's ClickHouse (empty: the service's own) and cluster name), managed by admins (`/api/source-types`, `/api/admin/instances[/:id]`, the PWA's `Instances.tsx` behind the twin menu in the bar, `InstanceMenu.tsx`: each twin's Settings and Models tabs — picking a twin there shows it, so its DTDL models are the ones `Models.tsx` edits); `/api/instances` lists the twins the user may see, and every twin route below lives under `/api/instances/:instance` (the PWA's `api.ts` prefixes them with the chosen twin, kept in the URL as `twin=` and in `localStorage`). The first start with none makes one from the old one-twin settings (`src/bootstrap.ts`: `CLUSTER_NAME` as its id, so its history goes on; it takes the one twin's dashboards and filters, `claimLegacy`, and the Osiris dashboard; once — deleted, it stays deleted).

**API** in the shape of Azure Digital Twins (`$dtId`, `$etag`, `$metadata.$model`; relationships `$relationshipId`/`$sourceId`/`$relationshipName`/`$targetId`): `/api/models[/:id]` (admins may also `PUT /models/:id`, `POST /models`, `DELETE /models/:id` — validated with `interfaceErrors`/`presentationErrors`, a delete refused with 409 while a twin instantiates the model), `/api/digitaltwins/:id` with `/relationships` and `/incomingrelationships`, plus the lists `/api/digitaltwins` and `/api/relationships` (live from Redis; `?at=` a past time from the history), `/api/digitaltwins/:id/history`, `/api/history/range`, `/api/events` (the collector's warn/error stream) and the models' telemetry `/api/telemetry/errorLogs`, `/api/telemetry/storage` (each volume claim's filesystem: `used`, `fsCapacity` from kubeletstats' `k8s.volume.capacity`/`available`, named by the claim only with the agent's `extra_metadata_labels: [k8s.volume.type]`, the adapter's `storageMetrics`, `Telemetry.latest`) and `/api/telemetry/network` (bytes/s of nodes and pods, the adapter's `networkMetrics`: kubeletstats' `k8s.node.network.io`/`k8s.pod.network.io`, rated over 5 minutes; `Telemetry.rates`; a twin without its own counter, like a microk8s node, carries its children's in the view). Live telemetry answers come from Redis (the sync writes them); `?at=` from ClickHouse.

**Models and sync.** Every model extends `dtmi:osiris:twin:Entity;1` (`name`, `status`, `otelResource` = the OpenTelemetry resource attributes of its telemetry, Telemetry `errorLogs`), and may carry a **`presentation`** section (`dtmi:osiris:presentation;1`: `look` — one of `LOOKS`, else the built-in of its DTMI, else a box; `color`, `icon`, `label` — a property name, `layer` — base/network/services/storage/logical, else the built-in of its DTMI (`BUILTIN_LAYERS`; a LoadBalancer or public interface is the services'), `visible`): the 3D view draws each twin as its model's presentation says (`buildScene` in `web/src/scene.ts`), so an admin changes the rendering by editing the model (the Models tab of a twin in the twins' administration, `Models.tsx`: a visual form and the DTDL in Monaco (`CodeEditor.tsx`, loaded on demand from the app's own build with the JSON worker, a theme made from the page's OSIRIS variables, a JSON schema of the supported DTDL and presentation while typing)). A **source adapter** (`TwinSource` in `src/twin.ts`: `models()`, `snapshot()`, `errorAttributes`, `networkMetrics`, `storageMetrics`) reads a system; `src/sync.ts` validates its models into SQLite (admin-edited ones are left alone) and every `SYNC_INTERVAL_SECONDS` diffs the snapshot against the last one in memory (`diffSnapshots` in `src/state.ts`), writes the after state and the view's telemetry into **Redis** (atomically, telemetry with a TTL) and sends what changed as **OpenTelemetry events** (`src/history.ts` `HistoryLog`, `eventEmitter` of `@osiris/platform/telemetry.ts`: `twin.entity`/`twin.relationship` log records with `twin.id` = the instance, `dt.*`/`rel.*` attributes and `dt.ancestors`, a checkpoint of everything once a day) into ClickHouse's `otel_logs`; `HistoryReader` rebuilds any time from the newest checkpoint plus the changes (30 days, the logs' TTL).

**The collector's events.** `deploy/observability/twin-events` is a Go processor (`twin_events`) built into the cluster's collector image (`builder-config.yaml`, ocb; `deploy/observability/collector.yaml` runs it in the `logs` and `logs/agents` pipelines): every log record at least `min_severity` (warn by default; the severity is inferred from the body like `SEVERITY_EXPR` when the record carries none) is appended to the Redis stream (XADD, MAXLEN-capped, best effort — ClickHouse never waits on it). The API serves it at `/events`, the agents at `/ops/events` (the `twin_events` tool in `packages/tools/digital-twin`), and with `EVENTS_PUSH*` the service pushes new events as runs of a thread to Osiris's gateway (`src/events.ts`).

**The 3D view.** The PWA (`web/src/scene.ts`) builds the view only from DTDL: `contains` nests twins, statuses and `errorLogs` roll up, labels and property formatting come from the models; children sit in a cube-like 3D grid (`arrange`/`cubeGrid` in `TwinLayout.ts`: columns, rows and layers from the floor up, groups by model lined up along the axis that keeps the whole nearest a cube; leaves are cubes), so the twin is a block rather than a plate; boxes have slightly rounded edges and storage (a model with Telemetry `used`) is a cylinder filled as far as it is full; twins whose model declares Telemetry `network` get a line from a hub (the bridge, else the router) on their container's back wall to their port or back wall with packets moving by their load, a pod's containers a line to its eth0 (`lan`), related siblings (a container `mounts` a claim) a line over their tops, and the cluster's hub reaches the internet, a globe behind it, by the sum of its nodes' traffic — every line is orthogonal (`orthogonal` in `TwinLayout.ts`: segments along one axis, right-angle turns, never straight across; network links run in a tray under the children's floor, wires and tunnels in lanes behind the back walls, routing and storage relations over the tops), ends on a wall, mantle, port or the globe, marked as an interface, and carries its layer (`Link.layer`) (`TwinLayout.ts`, `Twin3D.tsx`); a twin outside the containment tree that relates to one inside it groups it (`project` in `scene.ts`): the outermost group, a namespace, is a band — one dashed solid across the cluster around all of it, in every node and outside them (`measureBanded` in `TwinLayout.ts`: the nodes are columns, each band a row across them, what no node holds a wall-less column, what no band (disks, Ceph) the last row; the band rows go one behind another in levels stacked as high as keeps the cluster nearest a cube) — and the inner groups, workloads, are projections in each node (their telemetry is their group's on the node); each kind of twin has its own look (its model's `presentation.look`, else the built-in of its DTMI, `BUILTIN_LOOKS` in `@osiris/shared/dtdl.ts`: the cluster on a floor grid, a node with a status light, a namespace dashed and tinted, a workload dotted, a container solid, storage a filled cylinder, a disk with platters, Ceph (`ceph`) a drum with hoops and staves, its pools inside, a gauge on its lid as far round as it is full and a halo in its health's colour that pulses while unhealthy, an interface a port on its container's wall by its kind (a router a disc, a tunnel a hexagonal disc, a bridge a bar, the rest plates), a Service a hexagonal outline, an Ingress a portal — two posts and a beam with a breathing membrane, a lock on the beam with TLS, its hosts in its label), interfaces are wired (`wire`, `overlay` dashed for VXLAN), routing (Service → pods' eth0, Ingress → Service, LoadBalancer → Service) is drawn faint with the services layer and lit on the selection's traffic path (`pathOf`: public address → LoadBalancer → controller pods, Ingress → Service → pods → eth0 → router, lit with packets), storage relations (`hasOsd`, `holds`) dashed with the storage layer, lit when one end is selected; a twin, its lines and its address labels show only while its layer does (`hidden` in `Twin3D.tsx`); every solid has a label with its official Kubernetes icon as an outline (`k8s-icons.ts`, generated by `web/scripts/k8s-icons.mjs` from kubernetes/community's icon set, Apache-2.0 or CC-BY-4.0; `icons.ts`), its name, kind and state, shown by level of detail (the solid's size on screen); the 3D view is built once and repaints on refresh. Selected and hovered things glow in a bright cyan (`--accent-active`), errors are magenta (the twin's `--state-error`); interfaces with an address (pods, nodes, disks) show it beside their dot by level of detail.

**The bottom bar.** Under the 3D view one bar (`web/src/BottomBar.tsx`) holds everything: the time axis (`Timeline.tsx`), the display menu (`DisplayMenu.tsx`, a layers icon, opening upward within the window: the layer switches — network (interfaces, bridges, routers, tunnels), network services (Services, Ingresses, LoadBalancer and public addresses), storage, groupings; the base always shows —, the drawing options (`DisplayOptions`: labels by size, all or none, the addresses, moving traffic), and the filters — hidden models, a lowest status, a name search; all kept in this browser, the filters applied in the scene, `passes` in `scene.ts`), and the chat with Osiris (`OsirisChat.tsx`: the input in the bar — its left icon a menu of a new conversation and the earlier ones, newest first, from Osiris's `/threads` — the conversation a window, `chatPanel`). The keyboard moves inside the model (`Twin3D.tsx`): WASD/arrows pan, Q/E down/up, +/- zoom, Tab/Shift+Tab cycle the selection, H the whole twin, 1–4 one layer alone, 0 all of them.

**Interaction.** Hover names a box; a click selects it and the camera flies to center it with room around it, with its panels (`detailPanels` in `FocusPanels.tsx`: properties, a log tail of the 10 newest that loads older ones as it scrolls up, CPU/memory/network sparklines, traces) in windows over the twin joined to the box by SVG lines redrawn every frame; the first Escape closes the panels (the camera stays), the next flies back to the whole twin. **The windows** (`Windows.tsx`, the layout as data in `windowLayout.ts`) hold the selection's panels and the conversation with Osiris: each window a group of panels as tabs at a rectangle in fractions of the area; it moves by its header, snaps when dropped at an edge (a half), in a corner (a quarter) or at the top (maximized), joins another window as tabs when dropped on its header, lets a tab dragged out become a window of its own, resizes by its edges and corners, maximizes (button, double click) and has a menu doing the same without dragging; a closed panel stays hidden until the display menu shows it again (also "Default layout"). Below 720 px the windows are one, every panel a tab. The layout is the user's: `PUT /api/me/preferences/layout` (table `preferences`, owner and key, the same in every twin; `normalizeLayout` makes a stored one safe), cached in `localStorage`, saved 0.8 s after the last change. A time axis (`Timeline.tsx`) and each twin's Changes.

**Kubernetes adapter.** The one adapter is Kubernetes (`src/sources/kubernetes/`, models `;3`: namespaces, pods, nodes, replicasets → `contains` is physical: cluster → nodes (and unscheduled pods) → pods → containers and the PersistentVolumeClaims they mount (`PersistentVolumeClaim;1`, in the first pod by name, an unmounted one in the cluster; containers `mounts` it; the ClusterRole lists `persistentvolumeclaims`, without it the twin goes without them); the network (`network` in `graph.ts`, model `dtmi:osiris:net:Interface;1` with `kind` physical/router/bridge/tunnel/veth/loadbalancer/public): each node's card, router (Calico's routes, no bridge; with a bridge CNI — flannel's annotations — the host's, with the bridge `cni0` on the node's pod CIDR) and VXLAN tunnel (from the node's Calico or flannel annotations), each pod's `eth0` wired to its node's bridge, else its router (`connectedTo`), Services (`Service;1`, `routesTo` the pods of their EndpointSlices, a warning without ready ones) with their LoadBalancer addresses (MetalLB, `exposes`), Ingresses and Traefik IngressRoutes (`Ingress;1`, `routesTo` Services, `servedBy` the controller's LoadBalancer, an error for a missing Service), and the public addresses the Ingress hosts resolve to (`publicAddressesOf`; Cloudflare's addresses become one CDN interface in front of the cluster's own); namespaces and workloads relate by `hasNamespace`/`hasWorkload`/`hasPod`/`hasClaim`; with `CEPH_MANAGERS` (the managers' Prometheus pages, the active one answers; `sources/kubernetes/ceph.ts`) Ceph is a twin in the cluster with what watching it needs (health and the raised checks of `ceph_health_detail`, OSDs up/in, monitors in quorum, placement groups active+clean and degraded, client read/write bytes per second from the pools' counters between syncs) and its pools (`holds` the claims whose PV is an image in it), and its OSDs as disks (cylinders) in the nodes they're in, each filled by its own bytes (`ceph_osd_stat_bytes[_used]`), else by the cluster's average; namespaces and workloads carry their worst pod's status; ids are escaped paths `k8s:<cluster>/namespace/<ns>/pod/<pod>`).

**Pages and telemetry.** Telemetry and history answers are cached in the process (`memoryCache`). The twin is the PWA's only view under a see-through bar (pages centered, the user an avatar with a menu); the telemetry pages (Logy, Metriky, Trasy — the same ClickHouse queries the dashboard reads with) lie half see-through over it, closed by their tab again or Escape, and open filtered by the selected twin's `otelResource` (logs, traces and series take `namespace`, `pod`, `node`, `container`, `claim`). The first tab, Overview, opens a dashboard (with several, a menu asks which): named, shared dashboards (`/api/dashboards`, table `dashboards`, `Dashboard.tsx`) of panels — log bar charts, log records, metrics, traces — each with its page's filter and a width of four columns, over one time range; the pages add their current view to one ("+ Overview"). Logs show a bar chart of records over time by severity (`/api/logs/histogram`; hover shows a bar's counts, a click picks its time and level, a drag a span) and the user's saved filters (`/api/me/filters`, table `saved_filters` in `twin.db`, each user's own); their filters (service, namespace, node, pod, container from `/api/facets`, level, text searched as it's typed) live in the URL. A record's severity is its own, else read from its text (klog's prefix, a `level` field, the level's word, a Warning event; `SEVERITY_EXPR` in `telemetry.ts`), else info: most pods' output carries none, and the twin's error counts use the same. Without a token the PWA goes straight to sign-in (once a minute at most, so a failed sign-in never loops). The twin seeds an "Osiris" dashboard once (`src/dashboards.ts`).

**Osiris chat.** Osiris's agent lives over the twin (`OsirisChat.tsx`): the input at the bottom in the middle, the conversation a window over the twin (the state in `useOsirisChat`, shared by the input and the window), any earlier conversation opened from the history menu, voice messages (transcribed by Osiris, Mistral), answers read aloud (Piper), approvals as forms, and `twin_view`'s steps run on the view (select, turn/tilt/zoom through Twin3D's `control`, open pages, history); it calls Osiris through the twin's `/osiris/api/*` proxy (`OSIRIS_URL`, project `OSIRIS_PROJECT`) with the user's token, which osiris-gateway must accept from the `digital-twin` client.

**Sign-in and storage.** Sign-in is osiris-auth's: the PWA signs in as the public client `digital-twin` (PKCE), the API introspects as `osiris-digital-twin`: the group `admin` (`AUTH_ADMIN_GROUP`) sees and manages every twin, the group `twin:<id>` sees that twin (`maySee` in `auth.ts`; another twin answers 404), anyone else gets 403. `CLICKHOUSE_*` is the service's own ClickHouse (the history's, and a twin's telemetry when it names none); a twin's telemetry cluster name is the `k8s.cluster.name` its collector's resource/cluster processor stamps telemetry with. Controlling the twinned system (DTDL `Command`s, desired state, audit) would go to PostgreSQL.
