# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Multi-project SaaS assistant for tradespeople and small-business owners (jobs, scheduling, notes, invoices). A LangGraph agent runs per project in its own container. The clients are a web chat (Assistant UI) and WhatsApp. English is the canonical language of the code, docs and UI catalogs; the UI and the services' messages also ship in Czech (Slovak readers get Czech), and production's users write in Czech and Slovak. The agent's prompts, tool descriptions and tool results are Czech (see Internationalization).

## Commands

pnpm workspace, Node ≥ 24. Run these from the repo root:

```bash
pnpm install
pnpm --filter @osiris/platform gen-keys   # internal JWT key pair (+ master key) for gateway/control .env
node apps/osiris/bin/osiris.mjs <folder>  # the agent alone over a project folder (local mode), with the PWA, in a container (Linux; --no-container: a process; --build-image: the image from this repository)
node apps/osiris-cli/bin/osiris-cli.mjs [folder]  # the terminal client (starts the folder's agent if none runs)
pnpm dev                 # gateway (:3001), osiris-auth (:3003), control (:3002, starts project runtimes on :4100+), vitepress (:3005), web (:5173 → /api on :3001)
pnpm --filter @osiris/digital-twin dev   # the digital twin's API (:3004) and PWA (:5175); see server/digital-twin/CLAUDE.md
pnpm typecheck           # tsc in every package
pnpm test                # vitest in every service, shared (locale helpers, catalog checks) and web
pnpm --filter @osiris/agent exec vitest run test/app.test.ts   # one file
pnpm --filter @osiris/control exec vitest run -t "scheduler"     # by test name
```

There is no linter or formatter; `typecheck` and `test` are the checks.

Configuration lives in each app's `.env`, with `.env.example` next to it. Locally, control runs with the same SQLite file as in the cluster (`LOCAL_DB_PATH`), without S3 (folder), without SMTP (emails go to the log) and starts each project's runtime as a child process (`ORCHESTRATOR=local`), passing its own environment (model keys) on. To skip sign-in, set `AUTH_DEV_BYPASS=true` (gateway) and `VITE_DEV_USER=<name>` (web). The bearer token is then `<user>` (admin of their own project `<user>`) or `<user>:<claims>` to simulate claims, written like a query string (e.g. `bob:project=acme,beta`, `root:role=osiris-admin`; `role` defaults to `osiris-user`). A system admin creates projects in the web app first. To sign in for real locally, leave both unset, build osiris-auth's pages once (`pnpm --filter @osiris/auth-web build`, served from `server/auth/web/dist`), make control's SCIM token with `pnpm --filter @osiris/auth cli token control` (control's `AUTH_SCIM_TOKEN`), set the same `GATEWAY_CLIENT_SECRET` for osiris-auth and the gateway, and `pnpm --filter @osiris/auth cli add-admin <email>` prints a sign-in link (http://localhost:3003/link/…). Config validation refuses dev settings in production.

## Architecture

Layout: `apps/osiris` is the agent (`@osiris/agent`, the per-project runtime; Docker target `runtime`), `apps/osiris-pwa` the web client (`@osiris/pwa`), `server/*` the services of osiris-server, `packages/*` shared code; the clients `apps/osiris-desktop`, `apps/osiris-cli` and `apps/osiris-vscode` connect to a local agent or to the server.

Services (each `server/<name>` or `apps/osiris`, Hono on Node run by `tsx`, one Docker target per service):

- **auth** (osiris-auth, `server/auth`, https://auth.k6labs.cz on the busiris cluster, namespace `osiris-auth`, `deploy/auth`): an identity provider for any application, like PocketID: OpenID Connect sign-in, apps (`clients`), users and groups managed at `/admin`, the user's account page, its own SQLite (`DATA_DIR/auth.db`, one replica), SCIM 2.0 for other services and token introspection (RFC 7662) for registered APIs. Osiris is one of its apps. See **Sign-in**.
- **gateway**: the only entry from the internet for osiris.k6labs.cz. Has osiris-auth introspect API access tokens (`oidc.ts`, `POST <AUTH_URL>/introspect` as client `osiris-gateway` with `GATEWAY_CLIENT_SECRET`, cached 60 s per token), tells clients the issuer (`/auth-config.json`), works out memberships from the groups, and passes calls on with a short-lived **internal JWT** (`@osiris/platform/internal-auth.ts`, ES256, 60 s, audience `control` or `project:<slug>`): `/api/{me,admin,project,members,schedules,dashboards,analytics}` to control, everything else under `/api` to the active project's runtime. A sleeping runtime is woken (control → operator) and the request sent again, so request bodies are buffered (`MAX_BODY_MB`). Also serves the web build (with web-events' `/_e/e.js` in its manual mode when `WEB_EVENTS_SITE` is set; the app counts views as paths without ids, `wa.pageview`), security headers (CSP), per-user rate limits, and relays `/webhooks/whatsapp` to control.
- **control**: projects (table `projects`) and their members (users and groups are osiris-auth's: `users.ts` is a SCIM client with `AUTH_SCIM_TOKEN`, which maps control's claims to groups), WhatsApp (inbox + router), scheduler, project backups. Writes `Project` resources (`orchestrator/kubernetes.ts`, server-side apply) and nothing else in the cluster. Background loops run on every replica; work is claimed in the database.
- **runtime**: one process per project (`PROJECT_ID`), with the project folder on its volume (`DATA_DIR/project`: the project's files, its own data in `.osiris/`; see Project folder). The agent and all project routes of the old monolith (`app.ts`), plus `/internal/*` for control and the operator (`internal.ts`: activity, snapshot, scheduled runs, WhatsApp messages). Restores the newest snapshot when started on an empty volume. Features come from control (`RemoteFeatures`, cached 30 s).
- **operator**: reconciles `Project` objects (CRD `projects.osiris.k6labs.cz`, `deploy/k8s/crd.yaml`) into namespace `osiris-p-<slug>`: StatefulSet (0/1 replicas, own PVC), Service, ConfigMap/Secret (incl. the project's derived secrets key), NetworkPolicies, quota. Scale-to-zero: wakes on `spec.wakeRequestedAt`, and after `idleMinutes` without activity or running work takes a snapshot (`/internal/snapshot?reason=sleep`, the runtime then answers 503 `x-osiris-sleeping`) and scales to 0.
- **gotenberg**: shared HTML/office → PDF, no egress.
- **tts** (`server/tts`, Python, image `osiris-tts`): Piper text to speech (Czech `cs_CZ-jirka-medium`, English `en_US-lessac-medium`), `POST /tts {text, lang}` → WAV, reachable only from the gateway, no egress; the build speaks a sentence. The gateway's `/api/tts` (`TTS_URL`) serves signed-in users: the PWA reads answers aloud (`chat/speech.ts`, a 🔊 under each answer and a toggle in the composer; not on the public chat), the twin's chat too.
- **web-events** (`server/web-events`, namespace `observability`): cookieless web analytics for the cluster's sites (replacing GoatCounter): `/_e/e.js` and `POST /_e` on each site (IngressRoute in `deploy/observability/web-events.yaml`), a daily-salted visitor hash, never the IP; one OTLP log record per event to the collector's own `logs/web` pipeline → ClickHouse database `web` (`deploy/observability/web/schema.sql`: typed `web_events` and aggregate MVs), shown in Project > Traffic (the project's sites only: `projects.web_sites`, `/api/analytics`, feature `sites`). See `deploy/observability/web/README.md`.
- **vitepress** (`server/vitepress`): shared builder for `build_vitepress_site`: `POST /build` takes a site's source files (multipart, fields named by path) and answers the built files. The source runs code, so it has no secrets and no egress, builds one at a time in a fresh `/tmp` folder with an empty environment, and kills every other process after each build (`src/build.ts`; tini is PID 1 and reaps them). A project's one website is standard VitePress in its root: `.vitepress/` (the only hidden name the file store reaches) and the pages in `srcDir` (`web/` in a new site, so the project's other files never become pages); only those go to the builder, and the result replaces `.vitepress/dist/`.
- **digital-twin** (`server/digital-twin` + `server/digital-twin/web`, namespace `osiris`, https://twin.k6labs.cz): a general digital twin system as a 3D WebGL PWA (three.js). Models are DTDL v3 (`@osiris/shared/dtdl.ts`), the API follows Azure Digital Twins, and it holds any number of twins, each a source from a registry (today Kubernetes, optionally with Ceph) synced into its own SQLite (`twin.db`), with history as OpenTelemetry events in ClickHouse. It also runs the agent's `kubectl`/`ceph` (its ops API, see **Infrastructure**) and hosts Osiris's chat over the view. Its alerting is a service of its own, **digital-twin-alerts** (`server/digital-twin/src/alerts`): the collector's warn/error events become alerts that Osiris's agent investigates as a service account, each in its own conversation. Details in `server/digital-twin/CLAUDE.md` and `PLAN.md` there.

Packages: `packages/tools/*` (the agent's tool modules, see **Tool modules**), `packages/client` (the API client of every client: `connect({ url, token, signIn, locale })` once, then `api.*`; the PWA connects to its own origin with the OIDC token or a local agent's `#token=`), `packages/shared` (types and constants shared with the web client, file types, `theme.ts`: the OSIRIS palette for every client, checked against the PWA's `theme.css`; `material-icons.ts`: the Material Symbols (Outlined, Apache-2.0) the PWA and the twin's PWA draw with their `Icon.tsx`, generated by `scripts/material-icons.mjs` from `@material-symbols/svg-400` with only the icons it names: add a name there and run `pnpm --filter @osiris/shared icons`; no emoji or glyphs as icons, no icon font or CDN), `packages/platform` (internal JWT, control's SQLite (`LocalDb`), object storage, runtime identity, runtime client with wake-up, `SecretBox`, project key derivation), `packages/core` (the agent core used by the runtime: agent, checkpointer, RAG, MCP, vault, files, the project database, `projects/project.ts`). All are imported as TS source (`@osiris/<pkg>/<path>.ts`), with no build step. Paths like `agent/graph.ts` below are in `packages/core/src`.

**Sign-in** (`server/auth/src/`): osiris-auth is the OpenID Connect provider at its own origin (`oidc-provider`, `oidc.ts`; `server.ts` mounts it next to Hono, `OIDC_PATHS`, and sets `X-Forwarded-For` from trusted proxies only). **Apps** are rows of `clients` (`clients.ts`; the adapter's `Client` model reads them, so oidc-provider finds any registered app; metadata checked with `provider.Client.validate`): web or native, public (PKCE) or confidential (a secret sealed with a key from `AUTH_SECRET`, shown once, rotatable), redirect and post-logout URIs, `allowedGroups` (checked in `loadExistingGrant` on every authorization: outside them the app gets `access_denied`) and `acceptsTokensOf` (an API: it may introspect tokens issued to those apps at `/introspect` with its id and secret, and no others, so one app's token is never another's). Admins manage them at `/admin` (`/api/admin/clients`) or `cli.ts client add|list|remove`; Osiris's (`osiris-web`, `osiris-cli`, `osiris-vscode`, `osiris-gateway` with `GATEWAY_CLIENT_SECRET`) are registered at startup from `WEB_ORIGINS` when missing (`osirisClients`, never overwritten). A confidential app may name a **service account** (`serviceAccount`, a user id): with its id and secret it gets that user's tokens (client credentials), which introspection answers as that user with their groups, only while the app names it (the twin's alerting uses it; `cli.ts service-user` and `client update`). The only static client is `osiris-account`, the provider's own pages (`/account/signin` only starts the browser's session). No consent screen (every app is an admin's) and no self sign-up. Scopes `openid profile email groups`; tokens carry `groups`. Clients of Osiris find the issuer at the server's `/auth-config.json`. Refresh tokens rotate and live as long as the sign-in session (30 days); logout ends both. Its models (sessions, interactions, grants, codes, tokens) are rows of `oidc_store` (`DbAdapter`). **Pages** are the provider's own React app `server/auth/web` (`@osiris/auth-web`, in the PWA's design system: its `index.css` is imported; own catalogs; built into `web/dist`, `STATIC_DIR`): `/login` (`SignIn.tsx`, with the app's name and logo from `/interaction/:uid/state`), `/account` (profile with picture, `Security.tsx`, `AccountActivity.tsx`) and `/admin` for members of `ADMIN_GROUP` (`Admin.tsx`: users, groups, apps, API keys), named by `APP_NAME`/`APP_LOGO_URL` (`/api/config`, also in emails, passkeys and authenticator apps). The provider sends the browser to `/interaction/:uid`, which redirects to `/login?uid=`; the page calls the interaction API (`routes.ts`, every step checked against the interaction cookie, which oidc-provider reads from a stand-in Node request): password (argon2id via `node:crypto`), passkey (`@simplewebauthn/server`, discoverable, user verification required, so no second factor after it; they belong to the provider's own host, so they work for every app), Google/Facebook/Microsoft/Seznam (`social.ts`; the provider's callback `/social/:provider/callback` bounces sign-ins to `/interaction/:uid/social-callback`, where the cookie lives), a link by email. After a password, social or link sign-in a user with TOTP is asked for a code or a recovery code (`second-factor:<uid>` challenge). Verified Google/Facebook emails and Seznam mailboxes (@seznam.cz, @email.cz, …) match an existing user; Microsoft accounts must be linked from the account page. One-time links (`login_links`, invitations, admin links, email) are only remembered in a cookie at `/link/:token`; `?to=` (set when the link was made: an emailed link's own authorization, control's `<PUBLIC_URL>/?signin=link`) is followed only to this provider's `/authorize` or a registered web app's origin (`trustedReturn`), else `/account/signin`; the link is used up when that sign-in reaches `/interaction/:uid`, so mail scanners don't burn it. Single-use things (codes, links, challenges, TOTP steps) are taken with one conditional write. Failed attempts are limited per account, address and sign-in (`limiter.ts`). The browser's own API (`/api/me/profile`, `/api/me/picture`, `/api/me/security`, `/api/admin/*`) goes by the session cookie, changes only with the provider's own `Origin`. Emails go through Emailit's HTTP API (`@osiris/platform/mail.ts`, `EMAILIT_API_KEY`); `SMTP_URL` is the fallback. `AUTH_SIGNING_KEY` signs ID tokens; `AUTH_SECRET` derives the cookie keys, the TOTP sealing key and the client secrets' key. `pnpm --filter @osiris/auth cli add-admin|token|client|service-user` (`cli.ts`).

**Identity lives in osiris-auth.** Users (`users`, with `phone`) and groups (`groups`, `group_members`) are its own (`users.ts`). Other services use SCIM 2.0 (`scim.ts`, `/scim/v2`, bearer tokens of `service_tokens` made at /admin → API keys or `cli.ts token`; the admin pages use it with an admin's session): Users and Groups with filters `attr eq "value"` (joined by `and`), paging, POST/PUT/PATCH/DELETE, plus `POST /Users/:id/signInLink`, `PUT /Users/:id/photo` and `DELETE /Users/:id/secondFactor`, which SCIM has no standard for. A group's id is its name and never changes. The phone number is verified by the user sending `OVERENI <code>` from that phone to our WhatsApp number (control's `whatsapp/phones.ts`, written over SCIM). Profile pictures are on osiris-auth's volume, served at `<AUTH_URL>/pictures/<id>/<version>`; project logos are control's (`projects.logo`, set by project admins, `/project-logos/<id>/<version>` through the gateway).

**GeoIP and account activity**: shared local DB-IP City/ASN lookups (`packages/platform/src/geoip.ts`) and User-Agent parsing enrich web-events and osiris-auth's sign-in audit. Website analytics retains no IPs or account IDs; ClickHouse location/network aggregates back the extra Traffic panels. The sign-in audit (`server/auth/src/activity.ts`, table `auth_events`) retains IP and derived metadata for 90 days, visible only to the user on osiris-auth's account page (`AccountActivity.tsx`, `/api/me/security/activity`). Revoking `/api/me/security/sessions/:uid` checks ownership, deletes the OIDC session/tokens/grants and tombstones its UID against resurrection; adapter lookups check tombstones. The gateway's introspection cache delays enforcement up to 60 s. Last activity is updated at most every 5 minutes. The gateway resolves IPs with the shared trusted-proxy helper, not arbitrary client X-Forwarded-For. Control must remain reachable only through the gateway. Docker bundles GeoIP; daily checks fetch monthly releases into `/tmp`, retaining the last valid DB on failure. Apply the updated `deploy/observability/web/schema.sql` before deploying analytics code.

**Access = groups** (`@osiris/platform/claims.ts`). Every user needs group `osiris-user` or `osiris-admin`, otherwise 403. `project:<slug>` makes a user a member and `project-admin:<slug>` an admin. Tokens carry them (claim `groups`, introspection). Control still speaks in claims (`role`, `project`, `project-admin`, comma-separated) and its SCIM client turns each change into group memberships (`groupsFromAccess`, `accessFromGroups`); the dev bypass takes claims too. `osiris-admin` makes a system admin: admin of every project, with the project and user administration (`/api/admin/*`, "Projects" and "Users" in the web sidebar; users are created with a one-time sign-in link, edited, blocked, made system admins and given project roles there). Groups naming projects that don't exist (or are archived) are ignored; the gateway reloads its project list when one names an unknown project. Project admins manage their own project's people (`/api/members`): invite by email (an existing user joins, a new one is created and gets a one-time sign-in link), roles, removal.

**Service-to-service trust.** User calls carry the internal JWT signed by the gateway; control's and the operator's calls to runtimes are signed the same way (issuer `control`/`operator`). Runtimes hold only the public key and refuse tokens for another project. Runtimes call control with their projected ServiceAccount token (audience `osiris-control`), which control checks with TokenReview; the project is taken from the namespace, never from the request (`@osiris/platform/runtime-identity.ts`; locally `dev-runtime:<project>`). Project secrets are sealed with a per-project key derived from `SECRETS_MASTER_KEY` (HKDF, `project-keys.ts`), which only the operator holds.

**Control's database = one SQLite file** (`LocalDb` in `@osiris/platform/db.ts`, libSQL; migrations `server/control/src/db/migrations`, from one baseline `001_init.sql`: `migrate` takes a database from before it over when its history reaches the file's `-- baseline after:` and drops its `-- baseline drops:`, and refuses an older one; osiris-auth's the same) on its volume (`/data/control.db`, one replica, one writer, like osiris-auth). A batch of statements is atomic, and queues (WhatsApp inbox, schedules) are claimed with one conditional `UPDATE … WHERE id = (SELECT … LIMIT 1)` that stamps a claim token, read back by that token. Times are epoch ms passed in by the application, never `datetime('now')`.

**Features** (`ProjectFeatures`, column `projects.features`): a system admin switches `knowledge`, `skills`, `memory`, `mcp`, `http`, `whatsapp`, `files`, `scheduler`, `sites`, `integrations`, `public`, `database`, `workflows`, `infrastructure` and `customTools` per project (`FEATURES` in `@osiris/shared`; all on by default). **Quotas** (`projects.quotas`, set by system admins in the project's detail, null = no limit): file storage (MB; default 80 % of the volume, never above it), model tokens per calendar month (counted by the runtime from each response's `usage_metadata` in the project DB, `usage_months`; once used up the agent answers `TOKENS_EXHAUSTED` without calling the model), members (control refuses new ones), scheduled tasks (control), tokens per member per month (`tokensPerUserMonth`, rows `user:<sub>:YYYY-MM`; the member gets `USER_TOKENS_EXHAUSTED`), database tables and size (runtime) and the project's own dashboards (control). The runtime gets them with its features and reports their use at `/api/usage`, shown as meters above the project in the web sidebar. System admins also switch off single built-in tools per project (`projects.disabled_tools`, in the web's Tools and MCP view, listed by the runtime's `/api/tools`). The runtime resolves built-in tools as dynamic tools filtered by feature, switched-off tools and the project's `.osiris/tools.json` on every step, and the prompt drops switched-off sections. The runtime refuses routes of a switched-off feature (`FEATURE_ROUTES`), control refuses schedules, and the web app hides them.

**Project folder.** A project is a folder (`DATA_DIR/project` in its runtime) that may be a git working tree. Its own data is under `.osiris/` (`projects/records.ts`: `Records` reads and writes JSON and text records, writes through a synced temp file and rename, refuses hidden or `..` segments, and `lock`/`update` serialize read-modify-write per key in-process, since a project has exactly one runtime). Shared, versioned content: `project.json`, `tools.json`, `tools/` (own tools), `knowledge/`, `memory/`, `skills/<name>/SKILL.md`, `guards/`, `assistants/<name>/` (settings, `persona.json`, `guards/`), `mcp/`, `site/targets/`, `persona.json`. Everything personal or sealed is under `private/` (in `.osiris/.gitignore` with `cache/`, `tmp/` and `data.db`): `secrets/`, `mcp-headers/`, `mcp-oauth/`, `site-targets/`, `inquiries/`, `usage/<YYYY-MM>.json`, `runs/` (processed scheduled runs), `images/`, `threads/<thread>/` (`thread.json`, checkpoints, questions) and `users/<base64url sub>/` (settings, persona, memory, knowledge, skills, guards, MCP servers, secrets, accounts, integrations, WhatsApp session, files). There is no migration of older tenant databases: a project starts empty.

**Git** (`projects/git.ts`, Project > Git for admins, `/api/git`, feature `files`): a project folder can be a working tree of one https repository. Connecting checks out its branch over the project's files (or makes them the first commit of an empty one) and adds `.vitepress/dist/`, `.vitepress/cache/`, `node_modules/` to `.gitignore`; then commit (`add -A`, as the signed-in admin), pull (`--ff-only`; diverged → 409 naming the files) and push. Only the shared part of `.osiris/` is versioned (its `.gitignore` leaves out `private/`, `cache/`, `tmp/`, `data.db`). git runs through `execFile` with no user or system config, no hooks, `core.symlinks=false` and https only; the token is the project secret `GIT_TOKEN`, filled only for the remote's host and passed through `GIT_ASKPASS`, never in the URL. After connecting or pulling, `project.init()` brings indexes, memory and knowledge (by content hash) in step with the files. The runtime image has git.

**Local mode** (the PWA: `me.mode === "local"` hides Users, Traffic, the project Dashboard and the account's sign-in parts; the agent's link `/#token=…` is its sign-in, kept in `localStorage`; build it without `VITE_DEV_USER`) (`apps/osiris/src/cli.ts`, `local.ts`; the `osiris` command): the agent over a folder without osiris-server. Settings from the environment or `~/.config/osiris/agent.env`; the project id is the folder's name. It listens on `OSIRIS_HOST` (127.0.0.1) and `OSIRIS_PORT` (7777, else a free port), takes `.osiris/private/agent.lock` (`wx`; a second start while one is starting exits, a lock older than 2 minutes is a crash's), listens first and builds the project with `PUBLIC_URL` = its own address (OAuth sign-ins come back to it), then writes `.osiris/private/agent.json` (pid, port, url) for clients to find it and `.osiris/private/local-token` (0600): that token (`localAuth`, compared in constant time) makes the caller the project's admin, the computer's user named from git config. The project's secrets are sealed with a key derived from `~/.config/osiris/master.key`. `LocalFeatures`: everything but `whatsapp`, `scheduler`, `public`; no quotas or system rules. It answers `/api/me` (`mode: "local"`) and `/api/project` itself, every other server route with 404 `errors.local.serverOnly`, has no `/public` or `/internal` routes, allows any origin (CORS: the token is the key) and serves the PWA build. `index.ts` is the server mode (`serverConfig` requires PROJECT_ID, CONTROL_URL, INTERNAL_JWT_PUBLIC_KEY); both build the project with `build.ts`.

**Contained local agent** (`apps/osiris/src/launcher.ts`, `gate.ts`; Linux; Docker, or Podman with `OSIRIS_CONTAINER_CLI=podman`): `osiris <folder>` runs the agent in the image `ghcr.io/richardblaha/osiris-local` (Dockerfile target `local` = `runtime` + the PWA; the `.deb` pins its release's tag with `OSIRIS_IMAGE`, the repository uses `:main`, `--build-image` builds `osiris-local:dev`). The launcher holds the folder's lock and runs two containers named by the project id and a hash of the path (label `osiris.project`): the agent (`cli.ts` with `OSIRIS_CONTAINED=1`: read-only, `--cap-drop ALL`, `no-new-privileges`, memory and process limits, the user's uid, only the folder mounted at `/project`, `HOME=/tmp`) on an internal network (`--internal`), and the gate (`gate-cli.ts`, uid 65534) on that network and the bridge: its egress proxy (CONNECT only; resolves each name itself and connects to the checked address, refusing private, loopback, link-local, CGNAT and multicast, so the host and the LAN too, unless `OSIRIS_EGRESS_ALLOW=host[:port]`, e.g. `host.docker.internal:11434`) and the agent's port forwarded from the host's `127.0.0.1` (an internal network can't publish ports). Inside, `fetch` and `http`/`https` go through `HTTPS_PROXY` (`NODE_USE_ENV_PROXY=1`), git through `https_proxy`, and the clients with their own sockets through `tunnel()` (`packages/core/src/net/egress.ts`: POP3, nodemailer's `getSocket`, ImapFlow's `proxy`, ssh2's `sock`); with `OSIRIS_EGRESS_PROXY` set, `assertSafePublicUrl` leaves names to the gate. The container gets the project's derived secrets key (`OSIRIS_PROJECT_KEY`, deleted from its environment at start), never `master.key`; it and the model settings (`agent.env`, `MISTRAL_*`, `LLM_*`, …) pass as `-e NAME` from the launcher's environment, never on a command line. `agent.json` names the launcher's pid and the container; stopping the launcher stops both containers, and a start removes what a crash left. `--no-container`, `OSIRIS_CONTAINER=0` or a run inside a container already (`/.dockerenv`, `REMOTE_CONTAINERS`, `CODESPACES`: the devcontainer, VS Code there) start the agent as a process.

**osiris-cli** (`apps/osiris-cli`, Ink 8 = React for the terminal, run through tsx with its own tsconfig): the PWA's layout in the terminal, by width: sidebar (new chat, conversations, Context) | chat | the project's panel from 120 columns, sidebar | chat from 80, one pane below (Tab switches; detail lists replace the chat). The chat streams `RunEvent`s through `@osiris/client`, shows tool calls as steps and asks `ask_user` questions field by field (`@osiris-answer:`). Context lists are read-only (editing is the PWA's). Colors from `@osiris/shared/theme.ts` (dark unless `--theme=light` or COLORFGBG says light). Locally it finds `.osiris/private/agent.json` up from the folder or starts `osiris` detached; `osiris-cli login <url>` signs in to a server as the native OIDC client `osiris-cli` (PKCE, a loopback port; osiris-auth also registers `osiris-vscode`, both accepted by the gateway), keeping tokens in `~/.config/osiris/credentials.json` (0600); then `osiris-cli --server <url> [--project <id>]`. Texts Czech or English by the terminal's LANG. Tests draw it in a fake terminal of a given width.

**osiris-desktop** (`apps/osiris-desktop`, Tauri 2): its own page (`src/`, in the PWA's `theme.css` and font, copied by `scripts/theme.mjs` before a build) only chooses a project folder or a server, remembering recent ones; Rust (`src-tauri/src/lib.rs`) finds the folder's running agent or starts `osiris <folder> --port 0` (`OSIRIS_AGENT`, else PATH), stops the ones it started on exit, and navigates the window to the agent's `/#token=…` (its own PWA) or the server's URL. `osiris-desktop <folder>` opens the folder at once; the menu has Switch project. Every client shows the agent's startup error from `.osiris/private/agent-error` (written by `cli.ts`, removed by the client before it starts one). Builds need Rust and webkit2gtk; locally a Debian container works.

**osiris-vscode** (`apps/osiris-vscode`): a webview view `osiris.chat` in the secondary side bar (`viewsContainers.secondarySidebar`), `extensionKind: workspace` (in a devcontainer it and the agent run in the container, so `osiris` and Node 24 must be there). The host (`src/extension.ts`) finds the workspace folder's agent or starts it, a folder without `.osiris/` only after the panel's "Start Osiris in this folder" (`osiris.agentPath`: a command or a `bin/osiris.mjs`), hands the webview the address through `asExternalUri` (port forwarding) and every token on request (the webview never stores one), or signs in to `osiris.server` as `osiris-vscode` (`@osiris/client/oidc.ts`, shared with osiris-cli; PKCE, back through VS Code's URI handler `vscode://osiris.osiris-vscode/callback`, tokens in SecretStorage). The webview (`webview/`, React, esbuild) is VS Code's colors (`--vscode-*`) with the PWA's accents, the shared chat logic, question forms and an error boundary. Commands: open, new conversation, ask about the selection, connect to a server, use the local agent. `pnpm --filter osiris-vscode package` makes the `.vsix`. Every client checks that a running agent's port answers, not only its process id.

**Agent** (`agent/graph.ts`): a hand-built ReAct `StateGraph` (`agent` ↔ `tools`) over `MessagesAnnotation`, compiled once per runtime with tools bound to the project's stores (`projects/project.ts`). The built-in tools come from **tool modules** (see below). Per-run identity (`thread_id`, `project_id`, `user_id`, `role`, `channel`) is passed in `config.configurable` (`agent/context.ts`). The graph refuses a run whose `project_id` isn't its own. Tools read the user and role from the run context and never from model arguments. The system prompt is built per call, with the channel format, the date, the skill list, the files section and the user's memories, and is not checkpointed.

**Interactive chat** (`agent/questions.ts`, `private/threads/<thread>/questions/`): `ask_user` creates a durable, user/thread-scoped question with typed fields (text/number/date/select/multiselect/boolean), 24-hour expiry and atomic one-time answer consumption. The graph ends after the tool; validated answers start the next model step with the retained checkpoint history. Asking alongside any other tool rejects the entire batch. Cancellation and false confirmations are explicit; this is not a blanket authorization layer for arbitrary tools. PWA renders the tool result as a form, and polls completed remote thread snapshots every 5 seconds while visible. WhatsApp uses native reply buttons/lists; configured published Flows cover multi-field forms, otherwise a signed-in PWA link is sent. `@osiris-answer:` and `@osiris-attachments:` envelopes are validated server-side and not presented verbatim in user bubbles. Public chat supports questions, but no file uploads. Personal chat uploads to its thread's temp files and can record audio. Images are materialized into model requests only (checkpoint stores paths); text is inlined, PDF OCR is limited to the first 30 pages and audio uses configurable Mistral transcription. `send_chat_file` explicitly offers an existing file; WhatsApp file downloads require both ownership and an offer in the current turn. Control's `wa_deliveries` stores monotonic WhatsApp delivery statuses; the PWA's Profile shows them for the uniquely verified number (`WhatsAppDeliveries.tsx`, control's `/api/me/security/whatsapp-deliveries`). Setup, limits and a concrete Meta Flow JSON are in `deploy/whatsapp/README.md`; live Flow/template approval is external to the application.

**Infrastructure** (`packages/tools/kubernetes`, `packages/tools/ceph` and `packages/tools/digital-twin`, feature `infrastructure`; their shared client for the twin's ops API in `packages/tools/ops`, not a module): `kubectl`, `ceph`, `twin_query`, `twin_events` and `twin_view` for the projects in the runtime's `OPS_PROJECTS` (operator: `RUNTIME_ENV_OPS_URL`/`_OPS_PROJECTS`, today `twin`). **The agent's access is read-only**: kubectl and ceph never run in the isolated runtime; the digital twin's ops API (`server/digital-twin/src/ops.ts`, `/ops/kubectl|ceph`) runs them for runtimes of its own `OPS_PROJECTS` (projected token, TokenReview), only reads (`kubectlReads`/`cephReads` in `@osiris/shared/ops.ts`, which the tools check too and refuse without asking), without a shell, refusing identity/target options and interactive commands, capping time and output, logging each command (`ops.command`). kubectl runs as the `osiris-ops` ServiceAccount (ClusterRoles `view` and `osiris-ops-read`: no Secrets; its token secret mounted only into the twin, read through a kubeconfig's `tokenFile`), ceph with the optional `ceph-ops` secret (`ceph.conf`, `keyring`; `OPS_CEPH_USER`, a read-only key recommended). `twin_query` reads the twins, their models and objects with relationships (`/ops/twin/instances|models|digitaltwins[/:id]`, `?instance=`, else the first) with the same runtime token, no user's sign-in. Changes are the user's own, proposed by the agent in words. `twin_view` hands the twin's PWA view steps in its artifact. kubeadm doesn't apply (microk8s), nor microceph's own CLI (hosts only).

**Tool modules** (`packages/tools/<name>`, `@osiris/tools-<name>`; interface `ToolModule`/`ToolHost`/`ToolSet` in `packages/core/src/tools/module.ts`): every built-in tool lives in a package by function: `files` (file tools, `search_files`, `send_chat_file`), `knowledge`, `memory`, `skills`, `database`, `http`, `sites` (`publish_site`, `build_vitepress_site` only with `VITEPRESS_URL`), `integrations` (Google, Microsoft, SMTP/IMAP/POP3, CalDAV/CardDAV, `standard_accounts`), `images` (the whole image pipeline; only with `IMAGE_GENERATION_ENABLED`), `workflows` (the orchestrator and `run_workflow`), `scheduler` (server mode only, through control) and the cluster modules `kubernetes`, `ceph` and `digital-twin` (only with `OPS_URL`, for the projects in `OPS_PROJECTS`; their shared command client is `packages/tools/ops`, which has no module of its own). A module has one feature and `create(host)` returns its tools, plus optional `usable` (per-run filter: connected accounts, no `run_workflow` inside a workflow, image tools need `mcp`), `hidesMcpTool` and `init`. Core imports no tool package: the runtime's `apps/osiris/src/tool-modules.ts` imports with `import()` only the modules named in `TOOL_MODULES` (comma-separated, default `all`; an unknown name stops the start), so a module left out is never loaded and has no tools; `openProject` takes them as `deps.tools`. Per project the features (and switched-off tools) still filter the loaded modules' tools on every step. ask_user and the public assistants' tools stay in core. A new module is a package here, an entry in `MODULES` (its order is the tool list's), the runtime's dependency and two lines in the Dockerfile.

**Tool settings** (`packages/core/src/tools/config.ts`, `.osiris/tools.json`, read on every step): `{ "default": true, "modules": { "<module>": false }, "tools": { "<tool>": false } }` — a tool's own entry wins over its module's (the `MODULES` names, `custom` for the project's own tools, `mcp` for MCP tools), which wins over `default` (true). A tool runs only when its feature is on, a system admin hasn't switched it off (server) and the file allows it; `ask_user` is always there. A file that isn't valid switches every tool off (fails closed) and is logged. `/api/tools` marks `configOff`.

**Own tools** (`packages/core/src/tools/custom/`, feature `customTools`, module `custom`): each `.osiris/tools/<name>.ts|.mts|.js|.mjs` (name `^[a-z][a-z0-9_]{0,63}$`, not a built-in tool's; helpers may sit in subfolders) exports `default { description, input (JSON Schema, type object), run(input, ctx) }`, its result a string or JSON. Every describe (cached by mtime and size) and every call runs in a fresh process (`runner.mjs`): Node's permission model lets it read only the tools folder (no project data or keys, no child processes, no workers), with an empty environment, 128 MB heap, 30 s per call, 20 000 characters of result. Network isn't blocked by Node (the runtime's network policy applies on the server), but secrets reach it only through `ctx.fetch(url, { method, headers, body })`, which the runtime answers with `fetchWithSecrets` (`vault/fetch.ts`, shared with `http_request`: `{{secret:NAME}}` filled for allowed hosts, public addresses only, no redirects, secrets masked; 20 requests a call). TypeScript runs by Node's type stripping (erasable syntax only). The folder is under `.osiris/`, so neither the file API nor the agent writes it: own tools come from the folder itself (git or the local computer). Public assistants never get them.

**Web app layout.** The sidebar has Conversations, then Context (Knowledge, Memory, Files, Tools and MCP, Skills, Checks, Keys and passwords), Project (Dashboard, Assistants, Database, Scheduled tasks, Users, Websites, Traffic) and, for system admins, System (Dashboard, Diagnostics with Logs/Metrics/Traces tabs, Projects, Settings: `SystemDefaults` for new projects and users, split into Features, Limits, Operation and storage, Personalization and Persona subsections under `/system/settings/<part>`, `/api/admin/defaults`; the user defaults reach runtimes with the features). It collapses to icons. Lists show in a secondary panel (`MasterDetail.tsx`), and so do the profile's and the project's parts. Websites shows the project's one site (`/api/site`, a new one starts from `defaultTemplate`: `.vitepress/config.mjs` with `srcDir: "web"`), its pages, Build, "Publish to all" and each target with its own Publish.

**Project layer, personal layer.** The Context (knowledge, memory, files, skills, MCP servers, secrets) has two layers: the project's (owner `''`, memories `user_id` NULL), which everyone reads and only admins change, and each user's own (owner = sub), which only they see. A user's record with the same key (document id, file path, skill/server/secret name; a memory's `overrides`) replaces the project's for them: in their runs (search, prompt lists, tools, `{{secret:}}`, `read_file`/`render_template` of a project path) and marked `overridden` in their lists (`Layered` in `@osiris/shared`). APIs take `scope` (`project` needs an admin; default `personal`); the agent's `save_knowledge`/`remember` write the project's for admins and the user's own otherwise. The web shows both layers in one list (badges "personal"/"replaced"); a member opens a project record read-only with "Make my own copy" (`OwnCopy`), admins pick the scope of a new record (`ScopeChoice`); Files has Project/Mine tabs. Rules (guards) are not layered this way: a user adds their own, but never replaces the system's or project's. Only admins manage rules, the public assistant and sites. A user also keeps personalization: "My profile" (account, sign-in methods, phone, connected Google/Microsoft accounts) and the assistant settings (`user_settings`, `/api/settings`: address, language, signature, own instructions, plus a personal persona via `PUT /api/assistant?scope=personal`; the project has no persona, personalization is the user's), all of which go into the prompt below the rules. Conversations stay the user's own.

**Persona** (`agent/assistant.ts`, `persona.json` of each owner, owner `''` = project, a sub = the user's own, `@public:<name>` a public assistant's; `/api/assistant`): a persona is edited in one description textarea with an AI rewrite button in its bottom-right corner; the model expands the free-form brief (`POST /api/assistant/persona`), edited, then saved; the user's persona wins over the project's.

**Guards** (`agent/guards.ts`, the web's "Checks"): rules on four levels, one Markdown file per guard (frontmatter `name`, `description`, the rule as the body): system (control's table `system_guards`, system admins, `/api/admin/guards/:name`, reaches runtimes with the features), project (`.osiris/guards/<name>.md`, admins), user (`private/users/<base64url sub>/guards/`, the user's own) and public assistant (`.osiris/assistants/<name>/guards/`, admins); `/api/guards` and `/api/guards/:level/:name`. They are in `.osiris/`, which neither `/api/files` nor the agent's file tools reach, so no prompt lifts them. They go into the prompt above everything else, and when any exist the graph checks the user's message (`guard_in`, a refusal ends the turn) and the final answer (`guard_out`, replaced by id) with the model; the web then gets the answer only after the check (`streamRun(..., { guarded })`). A failing check lets the message through. The old one-text rules (`system_settings.guards`, `assistant_profiles.guards`) become a guard per line (`pravidlo-<n>`) once.

**Workflows** (`packages/tools/workflows`, feature `workflows`, tool `run_workflow`): the ReAct agent hands larger tasks to an orchestrator graph on its own thread `<thread>:workflow`. A router plans validated DAG steps (`state.ts`): ReAct (the agent itself, `reactFromAgentGraph`, on `<thread>:workflow:<step>` with `workflow: true` in the run context, so without `ask_user` and `run_workflow`), JEV/Reflexion (`jev.ts`: judge criteria, execute, deterministic verifiers `json`/`jsonld`/`dtdl`/`sql`, judge or critic; 3 repairs, then failed), MapReduce (`Send`, 4 at once). Ready steps run in parallel waves; destructive ones wait at `interrupt()`, which the tool turns into a chat question (`step_<n>` yes/no) and resumes only from the user's stored answer (`QuestionStore.answer`), never from model arguments. Nested graphs run `isolated()` from the caller's async local storage, otherwise LangGraph makes them the caller's subgraph and their interrupt ends the chat run. Each state change is an `AgentTelemetryEvent` (`@osiris/shared`, the router's carries `activeGraphTopology`), forwarded as `RunEvent` `telemetry`; `applyTelemetry` folds them into a `WorkflowView`, which the tool returns as its result's artifact (checkpointed, never shown to the model) and the chat draws live in the step (`chat/WorkflowDiagram.tsx`, one lane per step). A question another tool asks is checked against the rules like ask_user's arguments and withdrawn if it breaks them. Deleting a thread deletes the derived threads' checkpoints.

**Skills** (`agent/skills.ts`, tools `load_skill` and `save_skill`): the one bundled skill is `skill-creator` (`apps/osiris/skills/<name>/SKILL.md`, `SKILLS_DIR`; frontmatter `name` (kebab-case, same as the folder) and `description`, then Czech instructions; `requires: <feature>` offers a skill only while the project has that feature). Bundled skills are never copied into a project: they are a layer below the project's, so they are there whenever the feature `skills` is on, a project's (or user's) skill of the same name replaces one, and deleting that copy brings it back. They load at startup, and an invalid one stops the runtime from starting. Admins add project skills, and users their own, in the same layout, `.osiris/skills/<name>/SKILL.md` or the user's private folder (`/api/skills`, the agent's `save_skill`: the project's for admins, the user's own otherwise; editing them in the repository works too); personal wins over project, which wins over bundled. `SkillStore` reads the folders on every call and skips a malformed one. The prompt lists only name and description, and the model loads the body with `load_skill`. Projects seeded before keep their copies of the old bundled `crm` and `kontakty` as their own.

**Memory** (`agent/memory.ts`, `memory/mem0.ts`, `memory/file-vector-store.ts`): long-term facts through Mem0 (`mem0ai/oss`, telemetry off in `memory/env.ts`, imported before it): the project's (admins, Mem0 scope `agent_id: project`) and each user's own (`user_id`); a user's memory with `overrides` replaces that project memory for them (deleted with it). Mem0 runs on the project's LangChain models (`langchain` providers; the model wrapped to count its tokens to the payer in an `AsyncLocalStorage` and to hand LangChain answers to Mem0 as text) and on `FileVectorStore`, registered in Mem0's `VectorStoreFactory` as `osiris-files`: each memory is `memory/<id>.md` (a user's in their private folder) and each graph entity `memory/entities/<id>.md` (JSON payload as frontmatter, the text below), with vectors and an FTS5 keyword index in the cache (`mem0_points`, `mem0_text`), rebuilt from the files at init. `remember`, `forget` and `/api/memories` write verbatim (`infer: false`, then `link` for the entities); after each final answer (`learn` in the graph, not public or workflow runs, `MEMORY_LEARN`, on by default) Mem0 extracts the user's facts from the turn (`infer: true`, about 8k tokens a turn with Mistral Small, counted to the user). The prompt gets every memory while there are at most 100, else Mem0's search for the message. Mem0's entity heuristics are English: Czech words are cut at diacritics ("Novák" → "Nov"), which still links memories but reads oddly.

**MCP servers** (`mcp/`, `.osiris/mcp/<name>.json`, sealed headers in `private/mcp-headers/`): admins register the project's servers, users their own (`/api/mcp-servers`); a user's server replaces the project's of the same name in their runs. For members the API hides project server URLs, which may contain keys. Only http(s), never stdio. `mcp/url.ts` requires https and public addresses (SSRF); `MCP_ALLOW_PRIVATE` lifts that in development. The runtime's network policy also blocks every private range. Headers are sealed with the project's key, and the API returns only their names. A server can instead sign in with OAuth (`auth = 'oauth'`, `mcp/oauth.ts`): the MCP SDK's client with dynamic registration and PKCE over `mcp_oauth` (sealed client, tokens and verifier per server and owner); `POST /api/mcp-servers/:name/sign-in` gives the provider's URL, the provider returns the browser to the web app's `/mcp-callback`, which posts the code to `/api/mcp-oauth/callback` (only an admin finishes it). The web app offers presets: vas-hosting.cz (`https://portal.vas-hosting.cz/mcp`, OAuth) and Emailit (`https://api.emailit.com/mcp`, `Authorization: Bearer {{secret:EMAILIT_API_KEY}}`). `McpToolset` connects lazily per owner, one `MCPAdapter` per server so a failing server is skipped, caches tools for 5 minutes and closes idle personal connections after 15. Tool names are `<server>_<tool>`.

**Google and Microsoft accounts** (`integrations/`, feature `integrations`, `private/users/<sub>/integrations/`): a user connects their own account (My profile, `/api/integrations`; authorization code with PKCE against Osiris's OAuth clients `GOOGLE_INTEGRATION_CLIENT_*` / `MICROSOFT_INTEGRATION_CLIENT_*` in the runtime's env, redirect `<PUBLIC_URL>/integration-callback`; tokens sealed per user and refreshed). Built-in tools `google_*` (Gmail, People, Calendar APIs) and `microsoft_*` (Graph): mail search/read/send (and reply in a thread), contacts search/create/update, calendar events/create; a run gets only the tools of the accounts its user connected. Official Google/Microsoft MCP servers were passed over: Google's is read-only for contacts and can't send mail, Microsoft's needs a Copilot license and has no contacts.

**Standard accounts** (`integrations/standard.ts`; the protocols in `packages/tools/integrations/src/` `mail.ts`, `pop3.ts`, `dav.ts`): users connect named SMTP/IMAP/POP3, CalDAV and CardDAV accounts in Profile > Connected accounts (`/api/integrations/standard[/:name]`). Credentials are sealed in `standard_accounts`, never returned by the API; tools resolve the owner from run context. Feature `integrations` and disabled tool switches apply, public assistants cannot access them. `standard_accounts` lists account names; `mail_send` sends plain text with SMTP (implicit TLS or required STARTTLS), `mail_read` lists/reads without marking mail read (implicit TLS IMAP or read-only POP3 with UIDL ids). `caldav_read/save` and `carddav_read/save` discover collections and read/create/update RFC iCalendar/vCard data; updates require ETags. DAV discovery stays on the configured HTTPS origin (use the final canonical DAV URL), redirects are refused. SMTP/IMAP/POP3 hosts must resolve to public addresses, except with the existing development-only `MCP_ALLOW_PRIVATE`. No mail deletes, attachment downloads, or DAV deletes are exposed.

**Public assistants** (`public/assistant.ts`, feature `public`, `.osiris/assistants/<name>/`, the web's "Assistants"): a project has any number of assistants for its customers, each named (kebab-case) and configured by admins (`/api/public-assistants/:name`): title, greeting, token limit, the knowledge base documents and folders it searches (relative to `knowledge/`, matched by exact prefix), project memories it is told, project skills it may load, and the tools `estimate_price` (exact arithmetic over price list items) and `create_inquiry` (table `inquiries` with the assistant's name, admins emailed through control's `/internal/runtime/notify-admins`). Customers chat without signing in on `/c/<project>/<assistant>` (the web app's `PublicChat`, also inside `widget.js` with `data-assistant`, which projects put on their website; that page alone may be framed; without the assistant, or as `_`, the project's first). The gateway's `/public/<project>/*` takes a visitor id from the browser (`x-visitor-id`) and signs a call with only `visitor` (no user, no role), rate-limited per address; the runtime's `/public/<assistant>/*` (`publicAuth`) acts as `public:<visitor>` on channel `public` with `assistant` in the run context, whose threads nobody else can open. That channel gets `buildPublicPrompt` (customer-facing, the system's and project's rules plus its own, persona `@public:<name>` in `assistant_profiles`, `/api/assistant?assistant=<name>`) and only `publicTools`. Its tokens count for the project's quota and its own (`usage_months` row `public:<name>:YYYY-MM`). Answers always pass the output check before they're sent. The old single assistant (`project_settings.public_assistant`, `@public`, skills with `public: true`) moves to one named `web` at the project's init.

**Secrets** (`vault/`, `.osiris/private/secrets/<name>.json`): the project's API keys (admins) and users' own (a user's key of the same name is used in their runs; project MCP servers get project keys only), sealed and write-only (names, allowed hosts and descriptions only). Referenced as `{{secret:NAME}}` in MCP server URLs and headers and in `http_request` arguments, filled on the server by `SecretVault.fill`, only for `allowed_hosts`, never in a URL's scheme or host (`templateHost`). The prompt lists secret names and hosts.

**Database** (`database/store.ts`, `@osiris/tools-database`, feature `database`): the project's own SQLite file `.osiris/data.db` (in the snapshot, not in git), apart from the rest of `.osiris/` so the agent never reaches settings, threads or secrets. Tables get `id`, `created_at`, `updated_at`; columns are typed (`DB_COLUMN_TYPES`), with unique indexes and references (`ON DELETE SET NULL`/`RESTRICT`, foreign keys on: the store never opens a transaction, which would swap the connection). Writes are structured (`db_insert`/`db_update`/`db_delete` with an equality `where`); reading is one SELECT (`readOnlySql` refuses more statements, ATTACH, PRAGMA, VACUUM) run in a child process (`query-process.cjs`, `query_only`, killed after 5 s: SQLite can't be interrupted from JS, not even in a worker). Members fill rows, only admins shape or drop tables in the web (Project > Database, `/api/database`) and drop tables or columns through the agent. The prompt lists the tables.

**Dashboards** (`server/control/src/dashboards.ts`, table `dashboards`): System > Dashboard (system admins, `/api/admin/dashboards`) and Project > Dashboard (members see, admins edit, quota `dashboards`; `/api/dashboards`). Built-in ones (System, Websites, Usage) live in the web app (`Dashboards.tsx`), own ones are a JSON `DashboardDefinition`: panels of a kind (stat, line, bar, table, meters) over a `PanelSource`, which control checks per scope. The web loads each panel from the API that holds it and shapes it into a `PanelData` table: metric/logs/cluster (pods from `k8s.pod.phase`/`k8s.container.restarts`, Warning events from k8sobjects, projects from the `Project` status and backups), web (several sites at once, `webSummary`; a project sees `projects.web_sites` set in its detail), usage (runtime `/api/usage` and `/api/usage/breakdown`; every project's from `projects.usage`, which runtimes report to `/internal/runtime/usage` when it changes) and database (`/api/database/query`).

**Files** (`files/store.ts`, feature `files`): three scopes: the project folder itself (admins write; hidden names like `.osiris` and `.git` are never listed or reached), `.osiris/private/users/<base64url sub>/files/` (the user's own; a file at a project path replaces it for them) and `.osiris/tmp/<base64url thread>/` (a chat's scratchpad: kept until the chat is deleted, browsed in the chat's "Chat files" panel; a workflow step's runs use their chat's, `scratch_thread`; ones whose chat is gone are removed at the project's init). `FileStore` validates every path segment (no `..`, hidden names, backslashes or control characters), refuses to traverse symlinks, writes through a temp file and rename, accepts only the types in `@osiris/shared` `FILE_TYPES` with content matching the extension (magic bytes or valid UTF-8), and enforces `FILES_MAX_FILE_MB` and `FILES_QUOTA_MB`. The tools (`@osiris/tools-files`) take the scope as an argument but the user, role and thread from the run context. `render_template` uses Mustache (logic-less, no partials, HTML escaping only for markup; strict by default: a key the data lacks is refused by name, `missingKeys`), `edit_text` (`text-edit.ts` there) edits a text file in place (`replace_exact` that must match `expected_occurrences` times, `replace_regex` in a worker stopped after 200 ms, `insert_at`, `diff_patch`; `dry_run`; JSON answers with a unified diff), `resize_image` sharp, and `convert_to_pdf` exists only with `GOTENBERG_URL`. `/api/files` always serves downloads as attachments with `nosniff` and a sandbox CSP; temp files need `thread=` of the caller's own thread. The chat offers a download under tool calls that created a file.

**Scheduler** (`server/control/src/scheduler.ts`, feature `scheduler`): tasks (`schedules`) are a prompt with a 5-field cron (at most every 15 minutes) or a one-off time, run as their owner. A worker claims due tasks (lease 15 min), checks the owner is still in the project, wakes the runtime and calls `/internal/runs` with an idempotency key (`<id>:<due>`; the runtime answers a repeat from `processed_runs`). The result is a new web thread of the owner, optionally also sent to WhatsApp (only within 24 h of the user's last message). Runs more than an hour late are skipped; failures retry 3× with backoff. Users manage tasks in the web app or ask the agent (`schedule_task`, `list_schedules`, `cancel_schedule`, which call control).

**WhatsApp** (`server/control/src/whatsapp/`): one webhook for all projects (`/webhooks/whatsapp`, Meta's `X-Hub-Signature-256`), on when `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_APP_SECRET` and `WHATSAPP_ACCESS_TOKEN` are set, 404 otherwise. Messages are stored in `wa_inbox` (redeliveries dropped by message id) and answered at once; the router handles them one at a time per sender, in order: finds the user by `phone_number` (digits only; a number held by two users matches nobody), the project from their claims and `/project <slug>` choice (`wa_selection`), refuses projects with `whatsapp` off, and calls the runtime's `/internal/whatsapp/message`, which runs the agent in the user's WhatsApp thread (`whatsapp_sessions`, also listed in the web chat). `/nova` starts a new thread. Retries on an unreachable runtime, then replies with an apology.

**Backups** (`server/control/src/backups.ts`): runtimes stream snapshots (the project folder without `.osiris/cache`, plus a `VACUUM INTO` copy of `.osiris/data.db`, tar.gz) to control, which stores them under `backups/<project>/` (before every sleep, daily while awake, on demand from the project detail). Kept `BACKUP_RETENTION_DAYS`, at least the newest 3. Control's own database is copied daily by the `control-backup` CronJob (`VACUUM INTO`, to the volume and `backups/control/` in the bucket).

**Checkpointer** (`checkpointer/file-saver.ts`): `FileSaver` keeps the official `PostgresSaver` layout in files under `private/threads/<thread>/checkpoints/ns-<ns>/`: `cp/<id>.json` (checkpoint without channel values, metadata), `blobs/<channel>/<version>.json` (each channel value once per version, so history isn't duplicated in every checkpoint) and `writes/<id>/` (pending writes); bytes as base64. `apps/osiris/test/checkpointer.test.ts` runs the official `@langchain/langgraph-checkpoint-validation` suite (~700 tests) and must stay green after any change.

**Knowledge base and file search** (`rag/store.ts`, `files/index.ts`, `files/sync.ts`): the knowledge base is Markdown documents in `.osiris/knowledge/` (a user's own in their private folder; id = path like `cenik.md` or `public/cenik.md`, a `title` in frontmatter only when it isn't the leading heading). `/api/knowledge/documents[/:id]` and the agent's `save_knowledge` write them, and each is indexed as it's saved; `reindexStale` at init indexes those without chunks of the current embedding model and drops chunks of documents that are gone. `FileStore` reports every change (`onChange`) and `FileIndexer` keeps the full-text index of all text files (`file_text`, without diacritics; `/api/files/search`, the `search_files` tool) in step. Chunks are points of Mem0's collection (scope `agent_id: knowledge`, only in the cache, with `owner`, `path`, `idx`, `embedding_model`), inserted in a batch as a document is saved; `search_knowledge` is Mem0's search (meaning, BM25 words and entity boost) without a threshold, filtered to what the user may see. The cache is `.osiris/cache/index.db` (`projects/cache.ts`: `mem0_points`, `mem0_text`, `file_text`, `indexed_files`); a cache of another schema version is emptied and rebuilt at init. The website is built into `.vitepress/dist/` and published over SFTP to any number of targets (`sites/sftp.ts`, `.osiris/site/targets/<name>.json` with sealed credentials in `private/site-targets/`: server, folder, password or key sealed, host key pinned on the first connection; `/api/site-targets`, the `publish_site` tool, to one target or to all): only changed files go up, and only files listed in the remote `.osiris-manifest.json` (Osiris's own) are ever deleted. Domains and DNS are the hosting's (vas-hosting.cz through its MCP server). The web edits text files (Files, knowledge, skills) in Monaco (`CodeEditor.tsx`, bundled with its workers and loaded on demand, no CDN).

**Models** come from `provider:model` specs (`LLM_MODEL`, `EMBEDDING_MODEL`); defaults are Mistral Small 4 (`mistralai:mistral-small-2603`) and `mistralai:mistral-embed`, both via `MISTRAL_API_KEY`. System-only overrides `LLM_AGENT_MODEL` (first agent step), `LLM_TOOLS_MODEL` (reasoning after tool results), `LLM_GUARD_MODEL` (input/output checks), and `LLM_PERSONA_MODEL` (persona generation) inherit `LLM_MODEL` when unset. All default to Mistral; these are runtime environment settings, never project/user settings. Chat models go through LangChain `initChatModel`, so a new provider only needs its `@langchain/<provider>` package in `packages/core`. In the cluster the operator passes `RUNTIME_ENV_*` and `RUNTIME_SECRET_*` of its own environment to every runtime (without the prefix).

**Web streaming.** `POST /api/threads/:id/runs` sends only the new user message, because the runtime holds history in the checkpointer. It streams `RunEvent`s as SSE through the gateway: `status` as each graph node starts (thinking, tools, checking; checking only when rules apply), text tokens (held until the output check when rules apply), `tool-call-start` as soon as the model starts writing a call, then `tool-call` and `tool-result`. The chat shows each tool call as a step (running/done/failed, its arguments and result) and the status under the answer. `apps/osiris-pwa/src/chat/adapter.ts` turns them into Assistant UI parts for `useLocalRuntime`. History is loaded once via `GET /threads/:id/messages`. `ChatPane` is remounted (`key`) to switch threads. A new thread is created lazily on first send.

**Telemetry** (`@osiris/platform/telemetry.ts`): with `OTEL_EXPORTER_OTLP_ENDPOINT` set, every service sends traces, metrics and logs over OTLP (`startTelemetry` first in each `index.ts`): `console` output becomes log records tied to the active span (and still prints), outgoing `fetch` gets client spans and `traceparent` (undici instrumentation, no ESM hooks needed), and `telemetryMiddleware()` on each Hono root app makes server spans named by route plus a duration histogram. In the cluster they go to the OpenTelemetry Collector in namespace `observability` and on to ClickHouse (`deploy/observability`, with the whole cluster's pod logs, node and pod metrics and events); system admins explore the logs, metrics and traces at https://dashboard.k6labs.cz (the separate dashboard app; its telemetry API queries ClickHouse with a read-only user, every filter a query parameter) — Osiris keeps only the two endpoints its Dashboards panels need (`telemetry/`, `/api/admin/telemetry/logs` and `/series`, through control); runtimes get the endpoint through `RUNTIME_ENV_*` and an egress rule in the operator's network policy.

**Internationalization** (i18next; `packages/shared/src/i18n.ts`, `packages/platform/src/i18n.ts`, `apps/osiris-pwa/src/i18n.ts`). Locales are `LOCALES` (`en`, `cs`; BCP 47 language subtags), `en` is the source and the fallback; `matchLocale` maps tags to them (`cs-CZ` → `cs`, `sk` → `cs`, anything else → the fallback). The web app's catalogs are `apps/osiris-pwa/src/locales/<lang>/<namespace>.json` (one namespace per view, typed: `t("files:search")` is checked by `tsc`); its language is the user's `language` setting (`user_settings`, also the assistant's reply language; kept in `localStorage` `osiris.language`), else the browser's, else English. A language change re-renders the app (`main.tsx`), so components read texts with i18next's global `t`, and module-level texts must be functions. The web app sends its language as `Accept-Language` with every API call. Numbers, dates, sizes, lists and sorting go through `Intl` helpers in `apps/osiris-pwa/src/i18n.ts` (`formatDateTime`, `formatNumber`, `fileSize`, `formatList`, `compareText`, `initial`), never `"cs-CZ"`. The services' messages are one catalog, `packages/platform/src/locales/<lang>.json`: errors are `LocalizedError`/`HttpError(status, key, params)` (the English text is `message`, for logs and the agent's tool results) and each app's `onError` answers `{ error, code }` with `error` in the request's language (`requestLocale(Accept-Language)`) and `code` the catalog key; zod failures throw `ValidationError` (a schema's own messages are `errors.validation.*` keys, the rest zod's locale messages; parse with `reportInput: true`). Texts nobody requested in a language (WhatsApp replies, e-mails to others, notes stored with schedules, quota notices of scheduled and WhatsApp runs) use `DEFAULT_LOCALE` (env of control, gateway and runtimes; `cs` in `deploy/k8s`), else English. Runs carry `locale` in their context for the texts the run writes itself (quota notices, guard refusals, answer summaries, the attachments line). The agent's system prompts, tool descriptions and tool results stay Czech: they steer the model (changing them needs evaluation), and `chat/Thread.tsx` parses the file tools' results; the reply language comes from the user's setting ("Odpovídej …") or, on `auto`, the user's own messages. Bundled skills, the VitePress starter template and the legal pages (`apps/osiris-pwa/public/*.html`) are Czech content. `packages/shared/test/catalogs.test.ts` checks every catalog (keys per language, the plural forms each language needs, placeholders, `<Trans>` markup, duplicates, unused keys); CONTRIBUTING.md describes adding a language.

## Gotchas

- Auth tests (`server/auth/test/auth.test.ts`) need a real HTTP server, as oidc-provider is a Node handler: `browser()` in its helpers runs `authListener` on port 0 with a cookie jar that sends `x-forwarded-host`. Control's tests run osiris-auth in process (`createTestAuth`), reached over SCIM. Replaying an authorization code revokes the tokens it gave (OIDC), so don't redeem a code twice in a test that still uses its tokens.
- In runtime tests, `:memory:` libSQL loses data across `batch` transactions, so use `createTestCache()`, `createTestRecords()` (a fresh `.osiris/`) or `createTestProjects()` from `apps/osiris/test/helpers.ts`; `allText(records)` checks nothing is stored in the clear. `createTestApp(projects)` stands in for the gateway (dev tokens → internal JWT). `ScriptedChatModel` and `WordEmbeddings` replace real providers. Control tests use `createTestControl()` (temp SQLite with seeded users, fake orchestrator, runtimes, DNS, WhatsApp and mailer).
- Vitest runs with `globals: true` because the checkpoint validation suite needs Jest-style globals.
- Control's SQLite: never read-then-write expecting isolation; claim with a single conditional UPDATE. Pass times as parameters.
- Control's SQLite: polling loops must not write when there is nothing to do (check with a read first, then claim), so an idle poll churns no journal.
- `tar.c` returns a Minipass stream: wrap it in `Readable.from()` before `Readable.toWeb` or `pipe` into Node streams.
- Migration comments (control and osiris-auth) must not end a line with `;`, because the runner splits statements there. A new migration goes after `001_init.sql` (`002_…`); the baseline itself only changes when migrations are squashed again.
- In-process state (run guard, wake-up waits, rate limits, caches) is per replica by design: a project has exactly one runtime, and control has exactly one replica, so nothing needs to leave the process except through its SQLite.
- The workspace root `.env` and `.kubeconfig` hold local credentials and are gitignored. Never commit or print them.

## Release

A tag `vX.Y.Z` runs `.github/workflows/release.yml`: `osiris-cli_<v>_amd64.deb` (`packaging/deb/build-osiris-deb.sh`: the agent `osiris` and `osiris-cli` as a `pnpm deploy` of `@osiris/cli` in `/usr/lib/osiris/app`, the builder's Node 24 bundled, the PWA in `/usr/lib/osiris/pwa`, wrappers in `/usr/bin`; built on Ubuntu 22.04 for old glibc), `osiris-desktop_<v>_amd64.deb` (Tauri, recommends `osiris-cli`) and `osiris-vscode-<v>.vsix`, a GitHub Release with them, and for stable tags the `.deb` files in the signed APT repository `richardblaha/osiris-deb-repo` (GitHub Pages), rebuilt from its pool with osiris-theme's own `packaging/apt/build-apt-repo.sh` so both projects keep one repository (secrets `DEB_REPO_DEPLOY_KEY`, `APT_GPG_PRIVATE_KEY`). The agent's and the CLI's `files` keep development data out of the package; their launchers compile with tsx without the user folder's tsconfig.

## Deployment

Production runs at https://osiris.k6labs.cz in the `busiris` microk8s cluster: shared services in namespace `osiris`, each project in `osiris-p-<slug>`. CI pushes `ghcr.io/richardblaha/osiris-<service>` images on `main`, and the manifests live in `deploy/k8s` (kustomize). The gateway serves the web build (`STATIC_DIR`); sign-in is osiris-auth at https://auth.k6labs.cz (namespace `osiris-auth`, manifests in `deploy/auth`), which gateway, control and the digital twin reach through `AUTH_URL`. See `deploy/README.md` for secrets, sign-in (social apps, email, the past one-off import from control), WhatsApp, object storage, rollout and operations.
