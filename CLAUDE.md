# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Multi-tenant SaaS assistant for tradespeople and small-business owners (jobs, scheduling, notes, invoices). A LangGraph agent runs per tenant in its own container. The clients are a web chat (Assistant UI) and WhatsApp. English is the canonical language of the code, docs and UI catalogs; the UI and the services' messages also ship in Czech (Slovak readers get Czech), and production's users write in Czech and Slovak. The agent's prompts, tool descriptions and tool results are Czech (see Internationalization).

## Commands

pnpm workspace, Node ≥ 24. Run these from the repo root:

```bash
pnpm install
pnpm --filter @osiris/platform gen-keys   # internal JWT key pair (+ master key) for gateway/control .env
pnpm dev                 # gateway (:3001), control (:3002, starts tenant runtimes on :4100+), sites, web (:5173 → /api on :3001)
pnpm typecheck           # tsc in every package
pnpm test                # vitest in every service, shared (locale helpers, catalog checks) and web
pnpm --filter @osiris/runtime exec vitest run test/app.test.ts   # one file
pnpm --filter @osiris/control exec vitest run -t "scheduler"     # by test name
```

Configuration lives in each app's `.env`, with `.env.example` next to it. Locally, control runs without rqlite (SQLite file, which also holds the users), without S3 (folder), without SMTP (emails go to the log) and starts each tenant's runtime as a child process (`ORCHESTRATOR=local`), passing its own environment (model keys) on. To skip sign-in, set `AUTH_DEV_BYPASS=true` (gateway) and `VITE_DEV_USER=<name>` (web). The bearer token is then `<user>` (admin of their own tenant `<user>`) or `<user>:<claims>` to simulate claims, written like a query string (e.g. `bob:tenant=acme,beta`, `root:role=osiris-admin`; `role` defaults to `osiris-user`). A system admin creates tenants in the web app first. To sign in for real locally, leave both unset: `pnpm --filter @osiris/control users add-admin <email>` prints a sign-in link (http://localhost:5173/auth/link/…). Config validation refuses dev settings in production.

## Architecture

Services (each `apps/<name>`, Hono on Node run by `tsx`, one Docker target per service):

- **gateway**: the only entry from the internet. Passes `/auth/*` (sign-in) to control with cookies and redirects, has control identify API access tokens (`oidc.ts`, cached 60 s per token), works out memberships from the claims, and passes calls on with a short-lived **internal JWT** (`@osiris/platform/internal-auth.ts`, ES256, 60 s, audience `control` or `tenant:<slug>`): `/api/{me,admin,tenant,members,schedules,domains,sites}` to control, everything else under `/api` to the active tenant's runtime. A sleeping runtime is woken (control → operator) and the request sent again, so request bodies are buffered (`MAX_BODY_MB`). Also serves the web build (with GoatCounter's `count.js` when `GOATCOUNTER_URL` is set; the app counts views as paths without ids), security headers (CSP), per-user rate limits, and relays `/webhooks/whatsapp` to control.
- **control**: sign-in (the OpenID Connect provider, `auth/`), users and profiles (rqlite table `users`, `users.ts`), tenants (table `tenants`), WhatsApp (inbox + router), scheduler, custom domains, site publishing, tenant backups, legacy import. Writes `Tenant` resources (`orchestrator/kubernetes.ts`, server-side apply) and nothing else in the cluster. Background loops run on every replica; work is claimed in the database.
- **runtime**: one process per tenant (`TENANT_ID`), with the tenant's libSQL database and files on its volume (`DATA_DIR`: `db/tenant.db`, `files/`). The agent and all tenant routes of the old monolith (`app.ts`), plus `/internal/*` for control and the operator (`internal.ts`: activity, snapshot, scheduled runs, WhatsApp messages). Restores the newest snapshot when started on an empty volume. Features come from control (`RemoteFeatures`, cached 30 s).
- **operator**: reconciles `Tenant` objects (CRD `tenants.osiris.k6labs.cz`, `deploy/k8s/crd.yaml`) into namespace `osiris-t-<slug>`: StatefulSet (0/1 replicas, own PVC), Service, ConfigMap/Secret (incl. the tenant's derived secrets key), NetworkPolicies, quota; plus ingresses for verified site domains. Scale-to-zero: wakes on `spec.wakeRequestedAt`, and after `idleMinutes` without activity or running work takes a snapshot (`/internal/snapshot?reason=sleep`, the runtime then answers 503 `x-osiris-sleeping`) and scales to 0.
- **sites**: static tenant websites on custom domains; host → release from rqlite (read-only user), files from object storage.
- **gotenberg**: shared HTML/office → PDF, no egress.
- **web-events** (`apps/web-events`, namespace `observability`): cookieless web analytics for the cluster's sites (replacing GoatCounter): `/_e/e.js` and `POST /_e` on each site (IngressRoute in `deploy/observability/web-events.yaml`), a daily-salted visitor hash, never the IP; one OTLP log record per event to the collector's own `logs/web` pipeline → ClickHouse database `web` (`deploy/observability/web/schema.sql`: typed `web_events` and aggregate MVs), shown in Tenant > Traffic (the tenant's sites only: those of its domains and `tenants.web_sites`, `/api/analytics`, feature `sites`). See `deploy/observability/web/README.md`.
- **vitepress** (`apps/vitepress`): shared builder for `build_vitepress_site`: `POST /build` takes a site's source files (multipart, fields named by path) and answers the built files. The source runs code, so it has no secrets and no egress, builds one at a time in a fresh `/tmp` folder with an empty environment, and kills every other process after each build (`src/build.ts`; tini is PID 1 and reaps them). Tenants keep sources in `vitepress/<site>/` with `_vitepress/` for `.vitepress/` (the file store refuses hidden names); the tool writes the result to `www/<site>/`, replacing it.

Packages: `packages/shared` (types and constants shared with the web client, file types), `packages/platform` (internal JWT, rqlite client, object storage, runtime identity, runtime client with wake-up, `SecretBox`, tenant key derivation), `packages/core` (the agent core used by the runtime: agent, checkpointer, RAG, MCP, vault, files, tenant DB and migrations, `tenants/tenant.ts`). All are imported as TS source (`@osiris/<pkg>/<path>.ts`), with no build step. Paths like `agent/graph.ts` below are in `packages/core/src`.

**Sign-in** (`apps/control/src/auth/`): control is the OpenID Connect provider at `<PUBLIC_URL>/auth` (`oidc-provider`, `oidc.ts`; `server.ts` mounts it next to Hono, `OIDC_PATHS`). One first-party client `osiris-web` (public, PKCE, no consent screen: `loadExistingGrant` grants what it asks). Access tokens are opaque; the gateway asks `POST /internal/gateway/identify`. Refresh tokens rotate and live as long as the sign-in session (30 days); logout ends both. Its models (sessions, interactions, grants, codes, tokens) are rows of `oidc_store` (`DbAdapter`). The provider sends the browser to `/auth/interaction/:uid`, which redirects to the web app's `/login?uid=` (`SignIn.tsx`); the screen calls the interaction API (`routes.ts`, every step checked against the interaction cookie, which oidc-provider reads from a stand-in Node request): password (argon2id via `node:crypto`), passkey (`@simplewebauthn/server`, discoverable, user verification required, so no second factor after it), Google/Facebook/Microsoft/Seznam (`social.ts`; the provider's callback `/auth/social/:provider/callback` bounces sign-ins to `/auth/interaction/:uid/social-callback`, where the cookie lives), a link by email. After a password, social or link sign-in a user with TOTP is asked for a code or a recovery code (`second-factor:<uid>` challenge). Verified Google/Facebook emails and Seznam mailboxes (@seznam.cz, @email.cz, …) match an existing user; Microsoft accounts must be linked from the profile (the callback checks the browser's session belongs to the linking user). There is no self sign-up: users are invited or imported. One-time links (`login_links`, invitations, admin links, email) are only remembered in a cookie at `/auth/link/:token` and used up when the next sign-in reaches `/auth/interaction/:uid`, so mail scanners don't burn them. Single-use things (codes, links, challenges, TOTP steps) are taken with one conditional write. Failed attempts are limited per account, address and sign-in (`limiter.ts`, per replica). Profile security is `/api/me/security` (`securityRoutes`): password, passkeys, TOTP and recovery codes, linked accounts, never removing the last way in. Emails go through Emailit's HTTP API (`mail.ts`, `EMAILIT_API_KEY`), because Civo blocks outgoing SMTP; `SMTP_URL` is the fallback. `AUTH_SIGNING_KEY` signs ID tokens; `AUTH_SECRET` derives the cookie keys and the TOTP sealing key. `pnpm --filter @osiris/control users import-pocketid|add-admin` (`users-cli.ts`) imports PocketID's users with their ids and makes system admins.

**Identity lives in control.** Users are rows of `users` with their claims as JSON (`claims_version` for compare-and-swap writes). The phone number is the claim `phone_number`, verified by the user sending `OVERENI <code>` from that phone to our WhatsApp number (`whatsapp/phones.ts`). Profile pictures are in object storage, served at `/auth/pictures/<id>/<version>`; so are tenant logos (`tenants.logo`, set by tenant admins, `/auth/tenant-logos/<id>/<version>`).

**Access = claims** (`@osiris/platform/claims.ts`). Every user needs `role=osiris-user` or `role=osiris-admin`, otherwise 403. `tenant=<slug>` makes a user a member and `tenant-admin=<slug>` an admin (comma-separated list or JSON array). `role=osiris-admin` makes a system admin: admin of every tenant, with the tenant and user administration (`/api/admin/*`, "Tenants" and "Users" in the web sidebar; users are created with a one-time sign-in link, edited, blocked, made system admins and given tenant roles there). Claims naming tenants that don't exist (or are archived) are ignored; the gateway reloads its tenant list when a claim names an unknown one. Tenant admins manage their own tenant's people (`/api/members`): invite by email (an existing user joins, a new one is created and gets a one-time sign-in link), roles, removal.

**Service-to-service trust.** User calls carry the internal JWT signed by the gateway; control's and the operator's calls to runtimes are signed the same way (issuer `control`/`operator`). Runtimes hold only the public key and refuse tokens for another tenant. Runtimes call control with their projected ServiceAccount token (audience `osiris-control`), which control checks with TokenReview; the tenant is taken from the namespace, never from the request (`@osiris/platform/runtime-identity.ts`; locally `dev-runtime:<tenant>`). Tenant secrets are sealed with a per-tenant key derived from `SECRETS_MASTER_KEY` (HKDF, `tenant-keys.ts`), which only the operator and the legacy import hold.

**Central database = rqlite** (`@osiris/platform/rqlite.ts`, migrations `apps/control/src/db/migrations`). No interactive transactions: a batch is atomic, and queues (WhatsApp inbox, schedules) are claimed with one conditional `UPDATE … WHERE id = (SELECT … LIMIT 1)` that stamps a claim token, read back by that token with linearizable reads. Times are epoch ms passed in by the application, never `datetime('now')`. `LocalDb` (libSQL file) has the same interface for development and tests.

**Features** (`TenantFeatures`, column `tenants.features`): a system admin switches `knowledge`, `skills`, `memory`, `mcp`, `http`, `whatsapp`, `files`, `scheduler`, `sites`, `integrations`, `public` and `database` per tenant (all on by default). **Quotas** (`tenants.quotas`, set by system admins in the tenant's detail, null = no limit): file storage (MB; default 80 % of the volume, never above it), model tokens per calendar month (counted by the runtime from each response's `usage_metadata` in the tenant DB, `usage_months`; once used up the agent answers `TOKENS_EXHAUSTED` without calling the model), members (control refuses new ones), scheduled tasks (control), tokens per member per month (`tokensPerUserMonth`, rows `user:<sub>:YYYY-MM`; the member gets `USER_TOKENS_EXHAUSTED`), database tables and size (runtime) and the tenant's own dashboards (control). The runtime gets them with its features and reports their use at `/api/usage`, shown as meters above the tenant in the web sidebar. System admins also switch off single built-in tools per tenant (`tenants.disabled_tools`, in the web's Tools and MCP view, listed by the runtime's `/api/tools`). The runtime resolves built-in tools as dynamic tools filtered by feature and switched-off tools on every step, and the prompt drops switched-off sections. The runtime refuses routes of a switched-off feature (`FEATURE_ROUTES`), control refuses schedules and domains, and the web app hides them.

**Agent** (`agent/graph.ts`): a hand-built ReAct `StateGraph` (`agent` ↔ `tools`) over `MessagesAnnotation`, compiled once per runtime with tools bound to the tenant's stores (`tenants/tenant.ts`; the runtime adds schedule and site tools through `extraTools`). Per-run identity (`thread_id`, `tenant_id`, `user_id`, `role`, `channel`) is passed in `config.configurable` (`agent/context.ts`). The graph refuses a run whose `tenant_id` isn't its own. Tools read the user and role from the run context and never from model arguments. The system prompt is built per call, with the channel format, the date, the skill list, the files section and the user's memories, and is not checkpointed.

**Web app layout.** The sidebar has Conversations, then Context (Knowledge, Memory, Files, Tools and MCP, Skills, Checks, Keys and passwords), Tenant (Dashboard, Assistants, Database, Scheduled tasks, Users, Websites, Traffic) and, for system admins, System (Dashboard, Diagnostics with Logs/Metrics/Traces tabs, Tenants, Settings: `SystemDefaults` for new tenants and users, split into Features, Limits, Operation and storage, Personalization and Persona subsections under `/system/settings/<part>`, `/api/admin/defaults`; the user defaults reach runtimes with the features). It collapses to icons. Lists show in a secondary panel (`MasterDetail.tsx`), and so do the profile's and the tenant's parts. Files leaves out `skills/`, `guards/`, `vitepress/` and `www/`, which have their own views; Websites shows each site's `vitepress/<site>/` template (`/api/vitepress-sites`, a new site starts from `defaultTemplate`).

**Tenant layer, personal layer.** The Context (knowledge, memory, files, skills, MCP servers, secrets) has two layers: the tenant's (owner `''`, memories `user_id` NULL), which everyone reads and only admins change, and each user's own (owner = sub), which only they see. A user's record with the same key (document id, file path, skill/server/secret name; a memory's `overrides`) replaces the tenant's for them: in their runs (search, prompt lists, tools, `{{secret:}}`, `read_file`/`render_template` of a tenant path) and marked `overridden` in their lists (`Layered` in `@osiris/shared`). APIs take `scope` (`tenant` needs an admin; default `personal`); the agent's `save_knowledge`/`remember` write the tenant's for admins and the user's own otherwise. The web shows both layers in one list (badges "personal"/"replaced"); a member opens a tenant record read-only with "Make my own copy" (`OwnCopy`), admins pick the scope of a new record (`ScopeChoice`); Files has Tenant/Mine tabs. Rules (guards) are not layered this way: a user adds their own, but never replaces the system's or tenant's. Only admins manage rules, the public assistant and sites. A user also keeps personalization: "My profile" (account, sign-in methods, phone, connected Google/Microsoft accounts) and the assistant settings (`user_settings`, `/api/settings`: address, language, signature, own instructions, plus a personal persona via `PUT /api/assistant?scope=personal`; the tenant has no persona, personalization is the user's), all of which go into the prompt below the rules. Conversations stay the user's own.

**Persona** (`agent/assistant.ts`, table `assistant_profiles`, owner `''` = tenant, a sub = the user's own, `@public:<name>` a public assistant's; `/api/assistant`): a persona is edited in one description textarea with an AI rewrite button in its bottom-right corner; the model expands the free-form brief (`POST /api/assistant/persona`), edited, then saved; the user's persona wins over the tenant's.

**Guards** (`agent/guards.ts`, the web's "Checks"): rules on four levels, one Markdown file per guard (frontmatter `name`, `description`, the rule as the body): system (control's table `system_guards`, system admins, `/api/admin/guards/:name`, reaches runtimes with the features), tenant (`guards/<name>.md` in the tenant's files, admins), user (`guards/users/<base64url sub>/`, the user's own) and public assistant (`guards/assistants/<name>/`, admins); `/api/guards` and `/api/guards/:level/:name`. Members can't change `guards/` through `/api/files`, and the agent's file tools never write there, so no prompt lifts them. They go into the prompt above everything else, and when any exist the graph checks the user's message (`guard_in`, a refusal ends the turn) and the final answer (`guard_out`, replaced by id) with the model; the web then gets the answer only after the check (`streamRun(..., { guarded })`). A failing check lets the message through. The old one-text rules (`system_settings.guards`, `assistant_profiles.guards`) become a guard per line (`pravidlo-<n>`) once.

**Workflows** (`agent/orchestrator/`, feature `workflows`, tool `run_workflow`): the ReAct agent hands larger tasks to an orchestrator graph on its own thread `<thread>:workflow`. A router plans validated DAG steps (`state.ts`): ReAct (the agent itself, `reactFromAgentGraph`, on `<thread>:workflow:<step>` with `workflow: true` in the run context, so without `ask_user` and `run_workflow`), JEV/Reflexion (`jev.ts`: judge criteria, execute, deterministic verifiers `json`/`jsonld`/`dtdl`/`sql`, judge or critic; 3 repairs, then failed), MapReduce (`Send`, 4 at once). Ready steps run in parallel waves; destructive ones wait at `interrupt()`, which the tool turns into a chat question (`step_<n>` yes/no) and resumes only from the user's stored answer (`QuestionStore.answer`), never from model arguments. Nested graphs run `isolated()` from the caller's async local storage, otherwise LangGraph makes them the caller's subgraph and their interrupt ends the chat run. Each state change is an `AgentTelemetryEvent` (`@osiris/shared`, the router's carries `activeGraphTopology`), forwarded as `RunEvent` `telemetry`; `applyTelemetry` folds them into a `WorkflowView`, which the tool returns as its result's artifact (checkpointed, never shown to the model) and the chat draws live in the step (`chat/WorkflowDiagram.tsx`, one lane per step). A question another tool asks is checked against the rules like ask_user's arguments and withdrawn if it breaks them. Deleting a thread deletes the derived threads' checkpoints.

**Skills** (`agent/skills.ts`): bundled skills are folders `apps/runtime/skills/<name>/SKILL.md` (`SKILLS_DIR`) with frontmatter `name` (kebab-case, same as the folder) and `description`, followed by Czech instructions; `requires: <feature>` offers a skill only while the tenant has that feature (`kontakty` and `crm` need `database`). They load at startup, and an invalid skill stops the runtime from starting. Admins add tenant skills, and users their own, as files in the same layout, `skills/<name>/SKILL.md` in the tenant's or the user's files (`/api/skills` writes them; editing them in Files works too); personal wins over tenant, which wins over bundled. `SkillStore` reads the folders on every call and skips a malformed one. The prompt lists only name and description, and the model loads the body with `load_skill`.

**Memory** (`agent/memory.ts`, table `memories`): long-term facts of the tenant (`user_id` NULL, admins) and each user's own; a user's memory with `overrides` replaces that tenant memory for them (deleted with it). The model writes them with `remember` and `forget`, users manage them at `/api/memories`, and they're injected into the prompt as data, not instructions.

**MCP servers** (`mcp/`, table `mcp_servers`): admins register the tenant's servers, users their own (`/api/mcp-servers`); a user's server replaces the tenant's of the same name in their runs. For members the API hides tenant server URLs, which may contain keys. Only http(s), never stdio. `mcp/url.ts` requires https and public addresses (SSRF); `MCP_ALLOW_PRIVATE` lifts that in development. The runtime's network policy also blocks every private range. Headers are sealed with the tenant's key, and the API returns only their names. A server can instead sign in with OAuth (`auth = 'oauth'`, `mcp/oauth.ts`): the MCP SDK's client with dynamic registration and PKCE over `mcp_oauth` (sealed client, tokens and verifier per server and owner); `POST /api/mcp-servers/:name/sign-in` gives the provider's URL, the provider returns the browser to the web app's `/mcp-callback`, which posts the code to `/api/mcp-oauth/callback` (only an admin finishes it). The web app offers presets: vas-hosting.cz (`https://portal.vas-hosting.cz/mcp`, OAuth) and Emailit (`https://api.emailit.com/mcp`, `Authorization: Bearer {{secret:EMAILIT_API_KEY}}`). `McpToolset` connects lazily per owner, one `MCPAdapter` per server so a failing server is skipped, caches tools for 5 minutes and closes idle personal connections after 15. Tool names are `<server>_<tool>`.

**Google and Microsoft accounts** (`integrations/`, feature `integrations`, table `integrations`): a user connects their own account (My profile, `/api/integrations`; authorization code with PKCE against Osiris's OAuth clients `GOOGLE_INTEGRATION_CLIENT_*` / `MICROSOFT_INTEGRATION_CLIENT_*` in the runtime's env, redirect `<PUBLIC_URL>/integration-callback`; tokens sealed per user and refreshed). Built-in tools `google_*` (Gmail, People, Calendar APIs) and `microsoft_*` (Graph): mail search/read/send (and reply in a thread), contacts search/create/update, calendar events/create; a run gets only the tools of the accounts its user connected. Official Google/Microsoft MCP servers were passed over: Google's is read-only for contacts and can't send mail, Microsoft's needs a Copilot license and has no contacts.

**Public assistants** (`public/assistant.ts`, feature `public`, table `public_assistants`, the web's "Assistants"): a tenant has any number of assistants for its customers, each named (kebab-case) and configured by admins (`/api/public-assistants/:name`): title, greeting, token limit, the knowledge base documents and folders it searches (relative to `knowledge/`, matched by exact prefix), tenant memories it is told, tenant skills it may load, and the tools `estimate_price` (exact arithmetic over price list items) and `create_inquiry` (table `inquiries` with the assistant's name, admins emailed through control's `/internal/runtime/notify-admins`). Customers chat without signing in on `/c/<tenant>/<assistant>` (the web app's `PublicChat`, also inside `widget.js` with `data-assistant`, which tenants put on their website; that page alone may be framed; without the assistant, or as `_`, the tenant's first). The gateway's `/public/<tenant>/*` takes a visitor id from the browser (`x-visitor-id`) and signs a call with only `visitor` (no user, no role), rate-limited per address; the runtime's `/public/<assistant>/*` (`publicAuth`) acts as `public:<visitor>` on channel `public` with `assistant` in the run context, whose threads nobody else can open. That channel gets `buildPublicPrompt` (customer-facing, the system's and tenant's rules plus its own, persona `@public:<name>` in `assistant_profiles`, `/api/assistant?assistant=<name>`) and only `publicTools`. Its tokens count for the tenant's quota and its own (`usage_months` row `public:<name>:YYYY-MM`). Answers always pass the output check before they're sent. The old single assistant (`tenant_settings.public_assistant`, `@public`, skills with `public: true`) moves to one named `web` at the tenant's init.

**Secrets** (`vault/`, table `secrets`): the tenant's API keys (admins) and users' own (a user's key of the same name is used in their runs; tenant MCP servers get tenant keys only), sealed and write-only (names, allowed hosts and descriptions only). Referenced as `{{secret:NAME}}` in MCP server URLs and headers and in `http_request` arguments, filled on the server by `SecretVault.fill`, only for `allowed_hosts`, never in a URL's scheme or host (`templateHost`). The prompt lists secret names and hosts.

**Database** (`database/store.ts`, `agent/tools/database.ts`, feature `database`): the tenant's own SQLite file `DATA_DIR/db/data.db` (in the snapshot), apart from `tenant.db` so the agent never reaches settings, threads or secrets. Tables get `id`, `created_at`, `updated_at`; columns are typed (`DB_COLUMN_TYPES`), with unique indexes and references (`ON DELETE SET NULL`/`RESTRICT`, foreign keys on: the store never opens a transaction, which would swap the connection). Writes are structured (`db_insert`/`db_update`/`db_delete` with an equality `where`); reading is one SELECT (`readOnlySql` refuses more statements, ATTACH, PRAGMA, VACUUM) run in a child process (`query-process.cjs`, `query_only`, killed after 5 s: SQLite can't be interrupted from JS, not even in a worker). Members fill rows, only admins shape or drop tables in the web (Tenant > Database, `/api/database`) and drop tables or columns through the agent. The prompt lists the tables.

**Dashboards** (`apps/control/src/dashboards.ts`, table `dashboards`): System > Dashboard (system admins, `/api/admin/dashboards`) and Tenant > Dashboard (members see, admins edit, quota `dashboards`; `/api/dashboards`). Built-in ones (System, Websites, Usage) live in the web app (`Dashboards.tsx`), own ones are a JSON `DashboardDefinition`: panels of a kind (stat, line, bar, table, meters) over a `PanelSource`, which control checks per scope. The web loads each panel from the API that holds it and shapes it into a `PanelData` table: metric/logs/cluster (pods from `k8s.pod.phase`/`k8s.container.restarts`, Warning events from k8sobjects, tenants from the `Tenant` status and backups), web (several sites at once, `webSummary`; a tenant sees the sites of its domains plus `tenants.web_sites` set in its detail), usage (runtime `/api/usage` and `/api/usage/breakdown`; every tenant's from `tenants.usage`, which runtimes report to `/internal/runtime/usage` when it changes) and database (`/api/database/query`).

**Files** (`files/store.ts`, feature `files`): the runtime's `DATA_DIR/files` with three scopes: `tenant/` (admins write), `users/<base64url sub>/` (the user's own; a file at a tenant path replaces it for them) and `tmp/<base64url thread>/` (a chat's scratchpad: kept until the chat is deleted, browsed in the chat's "Chat files" panel; a workflow step's runs use their chat's, `scratch_thread`; ones whose chat is gone are removed at the tenant's init). `FileStore` validates every path segment (no `..`, hidden names, backslashes or control characters), refuses to traverse symlinks, writes through a temp file and rename, accepts only the types in `@osiris/shared` `FILE_TYPES` with content matching the extension (magic bytes or valid UTF-8), and enforces `FILES_MAX_FILE_MB` and `FILES_QUOTA_MB`. The tools (`agent/tools/files.ts`) take the scope as an argument but the user, role and thread from the run context. `render_template` uses Mustache (logic-less, no partials, HTML escaping only for markup; strict by default: a key the data lacks is refused by name, `missingKeys`), `edit_text` (`agent/tools/text-edit.ts`) edits a text file in place (`replace_exact` that must match `expected_occurrences` times, `replace_regex` in a worker stopped after 200 ms, `insert_at`, `diff_patch`; `dry_run`; JSON answers with a unified diff), `resize_image` sharp, and `convert_to_pdf` exists only with `GOTENBERG_URL`. `/api/files` always serves downloads as attachments with `nosniff` and a sandbox CSP; temp files need `thread=` of the caller's own thread. The chat offers a download under tool calls that created a file.

**Scheduler** (`apps/control/src/scheduler.ts`, feature `scheduler`): tasks (`schedules`) are a prompt with a 5-field cron (at most every 15 minutes) or a one-off time, run as their owner. A worker claims due tasks (lease 15 min), checks the owner is still in the tenant, wakes the runtime and calls `/internal/runs` with an idempotency key (`<id>:<due>`; the runtime answers a repeat from `processed_runs`). The result is a new web thread of the owner, optionally also sent to WhatsApp (only within 24 h of the user's last message). Runs more than an hour late are skipped; failures retry 3× with backoff. Users manage tasks in the web app or ask the agent (`schedule_task`, `list_schedules`, `cancel_schedule`, which call control).

**Sites** (feature `sites`): a tenant admin adds a custom domain (`domains`), proves it with a TXT record `_osiris-challenge.<domain>` and points it at the ingress (A records `SITES_INGRESS_IPS` or CNAME); control verifies through public DNS and re-checks every 6 h (a domain pointing elsewhere goes offline). Verified domains go into the Tenant spec, and the operator creates an ingress with an HTTP-01 certificate to the sites service. Publishing (`publish_site` tool or the Web view → `/api/site-publish` on the runtime) packs a folder with `index.html`, control validates every entry (regular files only, known types, size and count limits), uploads it as a new release (`sites/<tenant>/<release>/`) and switches the domain in one write; the last 5 releases are kept for rollback. Runtimes never hold S3 credentials.

**WhatsApp** (`apps/control/src/whatsapp/`): one webhook for all tenants (`/webhooks/whatsapp`, Meta's `X-Hub-Signature-256`), on when `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_APP_SECRET` and `WHATSAPP_ACCESS_TOKEN` are set, 404 otherwise. Messages are stored in `wa_inbox` (redeliveries dropped by message id) and answered at once; the router handles them one at a time per sender, in order: finds the user by `phone_number` (digits only; a number held by two users matches nobody), the tenant from their claims and `/tenant <slug>` choice (`wa_selection`), refuses tenants with `whatsapp` off, and calls the runtime's `/internal/whatsapp/message`, which runs the agent in the user's WhatsApp thread (`whatsapp_sessions`, also listed in the web chat). `/nova` starts a new thread. Retries on an unreachable runtime, then replies with an apology.

**Backups** (`apps/control/src/backups.ts`): runtimes stream snapshots (`VACUUM INTO` copy of the DB + files, tar.gz) to control, which stores them under `backups/<tenant>/` (before every sleep, daily while awake, on demand from the tenant detail). Kept `BACKUP_RETENTION_DAYS`, at least the newest 3. rqlite backs itself up to S3 (`rqlite-config` secret). The legacy import (`apps/control/src/legacy/`) turns the monolith's tenant databases into such backups, re-sealing secrets with the per-tenant keys.

**Checkpointer** (`checkpointer/libsql-saver.ts`): custom libSQL port of the official `PostgresSaver` layout. Channel values go to `checkpoint_blobs`, keyed by (channel, version), so message history isn't duplicated in every checkpoint. `apps/runtime/test/checkpointer.test.ts` runs the official `@langchain/langgraph-checkpoint-validation` suite (~700 tests) and must stay green after any change.

**Knowledge base and file search** (`rag/store.ts`, `files/index.ts`, `files/sync.ts`): the knowledge base is documents in the tenant DB (`knowledge_documents`, primary key owner and id like `cenik.md` or `public/cenik.md`, chunks keyed `knowledge/<id>` per owner), not files: `/api/knowledge/documents[/:id]` and the agent's `save_knowledge` write them, and each is indexed as it's saved; `reindexStale` at init indexes those without chunks of the current embedding model; the old `knowledge/` files move in once (`moveKnowledgeToDb`). `FileStore` reports every change (`onChange`) and `FileIndexer` keeps two indexes in the tenant DB in step: FTS5 over all text files (`file_text`, without diacritics; `/api/files/search`, the `search_files` tool) and the knowledge files' chunks (`knowledge_chunks` as libSQL `vector32`, plus `knowledge_text` FTS5). `search_knowledge` merges an exact `vector_distance_cos` scan (filtered by `embedding_model`) with word matches by reciprocal rank fusion. `tenant.init()` at startup moves old `documents`/`chunks` (rebuilt from overlapping chunks) and `skills` rows to files once, then reconciles the indexes with the files on disk (a restored snapshot). Changing `EMBEDDING_MODEL` hides old vectors until the files are indexed again. The website is the tenant's `www/`, published over SFTP to its hosting (`sites/sftp.ts`, table `site_targets`: server, folder, password or key sealed, host key pinned on the first connection; `/api/site-targets`, the `publish_site` tool): only changed files go up, and only files listed in the remote `.osiris-manifest.json` (Osiris's own) are ever deleted. Domains and DNS are the hosting's (vas-hosting.cz through its MCP server); the cluster's own sites service and domain verification are being retired. The web edits text files (Files, knowledge, skills) in Monaco (`CodeEditor.tsx`, bundled with its workers and loaded on demand, no CDN).

**Models** come from `provider:model` specs (`LLM_MODEL`, `EMBEDDING_MODEL`); defaults are Mistral Small 4 (`mistralai:mistral-small-2603`) and `mistralai:mistral-embed`, both via `MISTRAL_API_KEY`. System-only overrides `LLM_AGENT_MODEL` (first agent step), `LLM_TOOLS_MODEL` (reasoning after tool results), `LLM_GUARD_MODEL` (input/output checks), and `LLM_PERSONA_MODEL` (persona generation) inherit `LLM_MODEL` when unset. All default to Mistral; these are runtime environment settings, never tenant/user settings. Chat models go through LangChain `initChatModel`, so a new provider only needs its `@langchain/<provider>` package in `packages/core`. In the cluster the operator passes `RUNTIME_ENV_*` and `RUNTIME_SECRET_*` of its own environment to every runtime (without the prefix).

**Web streaming.** `POST /api/threads/:id/runs` sends only the new user message, because the runtime holds history in the checkpointer. It streams `RunEvent`s as SSE through the gateway: `status` as each graph node starts (thinking, tools, checking; checking only when rules apply), text tokens (held until the output check when rules apply), `tool-call-start` as soon as the model starts writing a call, then `tool-call` and `tool-result`. The chat shows each tool call as a step (running/done/failed, its arguments and result) and the status under the answer. `web/src/chat/adapter.ts` turns them into Assistant UI parts for `useLocalRuntime`. History is loaded once via `GET /threads/:id/messages`. `ChatPane` is remounted (`key`) to switch threads. A new thread is created lazily on first send.

**Telemetry** (`@osiris/platform/telemetry.ts`): with `OTEL_EXPORTER_OTLP_ENDPOINT` set, every service sends traces, metrics and logs over OTLP (`startTelemetry` first in each `index.ts`): `console` output becomes log records tied to the active span (and still prints), outgoing `fetch` gets client spans and `traceparent` (undici instrumentation, no ESM hooks needed), and `telemetryMiddleware()` on each Hono root app makes server spans named by route plus a duration histogram. In the cluster they go to the OpenTelemetry Collector in namespace `observability` and on to ClickHouse (`deploy/observability`, with the whole cluster's pod logs, node and pod metrics and events), which system admins read in System > Logy, Metriky, Trasy (control's `telemetry/`, `/api/admin/telemetry/*`, a read-only ClickHouse user, every filter a query parameter); runtimes get the endpoint through `RUNTIME_ENV_*` and an egress rule in the operator's network policy.

**Internationalization** (i18next; `packages/shared/src/i18n.ts`, `packages/platform/src/i18n.ts`, `apps/web/src/i18n.ts`). Locales are `LOCALES` (`en`, `cs`; BCP 47 language subtags), `en` is the source and the fallback; `matchLocale` maps tags to them (`cs-CZ` → `cs`, `sk` → `cs`, anything else → the fallback). The web app's catalogs are `apps/web/src/locales/<lang>/<namespace>.json` (one namespace per view, typed: `t("files:search")` is checked by `tsc`); its language is the user's `language` setting (`user_settings`, also the assistant's reply language; kept in `localStorage` `osiris.language`), else the browser's, else English. A language change re-renders the app (`main.tsx`), so components read texts with i18next's global `t`, and module-level texts must be functions. The web app sends its language as `Accept-Language` with every API call. Numbers, dates, sizes, lists and sorting go through `Intl` helpers in `apps/web/src/i18n.ts` (`formatDateTime`, `formatNumber`, `fileSize`, `formatList`, `compareText`, `initial`), never `"cs-CZ"`. The services' messages are one catalog, `packages/platform/src/locales/<lang>.json`: errors are `LocalizedError`/`HttpError(status, key, params)` (the English text is `message`, for logs and the agent's tool results) and each app's `onError` answers `{ error, code }` with `error` in the request's language (`requestLocale(Accept-Language)`) and `code` the catalog key; zod failures throw `ValidationError` (a schema's own messages are `errors.validation.*` keys, the rest zod's locale messages; parse with `reportInput: true`). Texts nobody requested in a language (WhatsApp replies, e-mails to others, notes stored with schedules and domains, quota notices of scheduled and WhatsApp runs) use `DEFAULT_LOCALE` (env of control, gateway and runtimes; `cs` in `deploy/k8s`), else English. Runs carry `locale` in their context for the texts the run writes itself (quota notices, guard refusals, answer summaries, the attachments line). The agent's system prompts, tool descriptions and tool results stay Czech: they steer the model (changing them needs evaluation), and `chat/Thread.tsx` parses the file tools' results; the reply language comes from the user's setting ("Odpovídej …") or, on `auto`, the user's own messages. Bundled skills, the VitePress starter template and the legal pages (`apps/web/public/*.html`) are Czech content. `packages/shared/test/catalogs.test.ts` checks every catalog (keys per language, the plural forms each language needs, placeholders, `<Trans>` markup, duplicates, unused keys); CONTRIBUTING.md describes adding a language.

## Gotchas

- Auth tests (`apps/control/test/auth.test.ts`) need a real HTTP server, as oidc-provider is a Node handler: `controlListener` on port 0 and a cookie jar that sends `x-forwarded-host`. Replaying an authorization code revokes the tokens it gave (OIDC), so don't redeem a code twice in a test that still uses its tokens.
- In runtime tests, `:memory:` libSQL loses data across `batch` transactions, so use `createTestDb()` or `createTestTenants()` from `apps/runtime/test/helpers.ts`. `createTestApp(tenants)` stands in for the gateway (dev tokens → internal JWT). `ScriptedChatModel` and `WordEmbeddings` replace real providers. Control tests use `createTestControl()` (temp SQLite with seeded users, fake orchestrator, runtimes, DNS, WhatsApp and mailer).
- Vitest runs with `globals: true` because the checkpoint validation suite needs Jest-style globals.
- rqlite: never read-then-write expecting isolation; claim with a single conditional UPDATE. Pass times as parameters.
- rqlite: polling loops must not write when there is nothing to do. An UPDATE that changes no rows still adds a Raft log entry, and rqlite can't snapshot (and so truncate the log) without new data, so the log grows forever. Check with a read first, then claim.
- `tar.c` returns a Minipass stream: wrap it in `Readable.from()` before `Readable.toWeb` or `pipe` into Node streams.
- Migration comments (tenant and central) must not end a line with `;`, because the runners split statements there.
- In-process state (run guard, wake-up waits, rate limits, caches) is per replica by design: a tenant has exactly one runtime, and everything shared between control replicas goes through rqlite.
- The workspace root `.env` and `.kubeconfig` hold local credentials and are gitignored. Never commit or print them.

## Deployment

Production runs at https://osiris.k6labs.cz in the `abydos` k3s cluster: shared services in namespace `osiris`, each tenant in `osiris-t-<slug>`. CI pushes `ghcr.io/richardblaha/osiris-<service>` images on `main`, and the manifests live in `deploy/k8s` (kustomize). The gateway serves the web build (`STATIC_DIR`); sign-in is on the same origin (`/auth`). PocketID (auth.k6labs.cz) stays in the cluster for other services, Osiris doesn't use it. See `deploy/README.md` for secrets, sign-in (social apps, SMTP, the import from PocketID), WhatsApp, object storage, rollout, the one-off import from the monolith and operations.


**Standard accounts** (`integrations/standard.ts`, `mail.ts`, `pop3.ts`, `dav.ts`): users connect named SMTP/IMAP/POP3, CalDAV and CardDAV accounts in Profile > Connected accounts (`/api/integrations/standard[/:name]`). Credentials are sealed in `standard_accounts`, never returned by the API; tools resolve the owner from run context. Feature `integrations` and disabled tool switches apply, public assistants cannot access them. `standard_accounts` lists account names; `mail_send` sends plain text with SMTP (implicit TLS or required STARTTLS), `mail_read` lists/reads without marking mail read (implicit TLS IMAP or read-only POP3 with UIDL ids). `caldav_read/save` and `carddav_read/save` discover collections and read/create/update RFC iCalendar/vCard data; updates require ETags. DAV discovery stays on the configured HTTPS origin (use the final canonical DAV URL), redirects are refused. SMTP/IMAP/POP3 hosts must resolve to public addresses, except with the existing development-only `MCP_ALLOW_PRIVATE`. No mail deletes, attachment downloads, or DAV deletes are exposed.


**GeoIP and account activity**: shared local DB-IP City/ASN lookups (`packages/platform/src/geoip.ts`) and User-Agent parsing enrich web-events and control auth. Website analytics retains no IPs or account IDs; ClickHouse location/network aggregates back the extra Traffic panels. Login audit (`auth/activity.ts`, migration 009) retains IP and derived metadata for 90 days, visible only to the user at `/api/me/security/activity`, Profile > Activity and sessions. Revoke `/api/me/security/sessions/:uid` checks ownership, deletes the actual OIDC session/tokens/grants and tombstones its UID against resurrection; adapter lookups check tombstones with linearizable reads. Gateway cache delays enforcement up to 60 s. Last activity is updated at most every 5 minutes. Gateway resolves IPs with the shared trusted-proxy helper, not arbitrary client X-Forwarded-For. Control must remain reachable only through the gateway. Docker bundles GeoIP; daily checks fetch monthly releases into `/tmp`, retaining the last valid DB on failure. Apply the updated `deploy/observability/web/schema.sql` before deploying analytics code.


**Interactive chat** (`agent/questions.ts`, migration 019): `ask_user` creates a durable, user/thread-scoped question with typed fields (text/number/date/select/multiselect/boolean), 24-hour expiry and atomic one-time answer consumption. The graph ends after the tool; validated answers start the next model step with the retained checkpoint history. Asking alongside any other tool rejects the entire batch. Cancellation and false confirmations are explicit; this is not a blanket authorization layer for arbitrary tools. PWA renders the tool result as a form, and polls completed remote thread snapshots every 5 seconds while visible. WhatsApp uses native reply buttons/lists; configured published Flows cover multi-field forms, otherwise a signed-in PWA link is sent. `@osiris-answer:` and `@osiris-attachments:` envelopes are validated server-side and not presented verbatim in user bubbles. Public chat supports questions, but no file uploads. Personal chat uploads to its thread's temp files and can record audio. Images are materialized into model requests only (checkpoint stores paths); text is inlined, PDF OCR is limited to the first 30 pages and audio uses configurable Mistral transcription. `send_chat_file` explicitly offers an existing file; WhatsApp file downloads require both ownership and an offer in the current turn. Control migration 010 stores monotonic WhatsApp delivery statuses; Profile > Activity and sessions shows them for the uniquely verified number. Setup, limits and a concrete Meta Flow JSON are in `deploy/whatsapp/README.md`; live Flow/template approval is external to the application.
